# 설계 결정 이력 (ADR)

새 결정은 맨 아래에 추가한다. 기존 항목은 지우지 않는다.
결정을 뒤집을 때는 해당 항목의 상태를 `Superseded by ADR-NNN`으로 바꾸고 새 항목을 추가한다.

상태: `Accepted` / `Proposed` / `Superseded` / `Rejected`

## ADR-001 — 백엔드는 Go, MSA로 쪼개지 않는다
**상태:** Accepted

**맥락:** MSA 구성을 검토했다. 도메인이 수집·번역 둘뿐이고 1인 개발 규모다.

**결정:** Go 모듈 하나에 `cmd/api`, `cmd/worker` 두 바이너리. 서비스를 더 쪼개지 않는다.
확장이 필요하면 같은 바이너리를 다른 큐만 소비하도록 추가 기동한다.

**결과:** 배포 단위가 적어 Railway 운영이 단순하다. 도메인 경계가 검증된 뒤에야 분리를 재검토한다.

---

## ADR-002 — 배포는 Railway
**상태:** Accepted

**맥락:** 초기 규모에 맞는 관리형 플랫폼이 필요했다.

**결정:** Railway. api / worker / postgres / web 네 서비스.

**결과:** k8s 프리미티브(서비스 메시, 카나리)는 쓸 수 없다. 관측성은 외부 도구(OTel)를 붙여야 한다.
프라이빗 네트워크가 IPv6 전용이라 `[::]` 바인딩이 강제된다.

---

## ADR-003 — 잡 큐는 River (Redis 아님)
**상태:** Accepted

**맥락:** asynq(Redis)와 River(Postgres)를 비교했다.

**결정:** River. Postgres 트랜잭션 안에서 enqueue가 가능한 것이 결정적이었다.
"책 레코드는 생성됐는데 잡 등록이 실패"하는 틈이 생기지 않는다.

**결과:** Railway 서비스가 하나 줄어든다(Redis 불필요). 처리량 한계는 Postgres에 종속된다.

## ADR-004 — 번역은 `paragraph_stable_id`에 결합한다
**상태:** Accepted

**맥락:** 파서를 개선해 재파싱하면 문단 행 ID가 밀린다. 번역이 `paragraphs.id`를 참조하면
모든 번역이 엉뚱한 문단에 붙는다.

**결정:** `stable_id = sha256(정규화된 본문)[:16]`. 번역 테이블은 FK 대신 이 값을 참조한다.
파싱 결과는 불변 `book_revisions`로 쌓는다.

**결과:** FK 무결성을 포기하는 대신 재파싱이 안전해진다. revision 전환 시 해시 매칭으로 승계한다.
이 프로젝트에서 가장 되돌리기 어려운 지점이므로 우선순위가 높다.

**보완:** 같은 본문이 한 책에 반복되면 이 정의만으로는 번역 행이 공유된다.
2번째 등장부터 등장 순서를 붙이는 규칙을 **ADR-016**에서 더했다. 이 항목을 뒤집지는 않는다 —
첫 등장의 `stable_id`는 위 정의 그대로다. 전체 규칙은 `docs/ARCHITECTURE.md` 핵심 불변식 1 참조.

## ADR-005 — 문단당 확정 번역 1개를 스키마로 강제한다
**상태:** Accepted

**맥락:** 여러 사용자가 제안하고 검수를 거쳐 하나만 공개하는 모델이다.

**결정:** `translation_proposals`(N개)와 `paragraph_translations`(0 또는 1개)를 분리하고,
후자에 복합 PK `(project_id, paragraph_stable_id)`를 건다.
승인은 한 트랜잭션 안에서 처리하며 `WHERE status = 'pending'` 조건으로 동시 승인을 막는다.

**결과:** 불변식이 애플리케이션이 아니라 DB에서 지켜진다.

## ADR-006 — 웹은 TanStack Start (SSR)
**상태:** Accepted

**맥락:** 검색 노출이 필요하다. Go 템플릿 + 별도 SPA, Next.js, TanStack Start를 비교했다.

**결정:** TanStack Start. 2026-03 v1.0 릴리스로 안정화됐다.
읽기 화면은 SSR, 편집·검수 화면은 CSR로 **같은 라우터 안에서** 라우트별로 나눈다.

**결과:** 프론트를 두 벌 만들지 않아도 된다. 대신 Node 서비스가 하나 늘고,
API 베이스 URL을 서버·클라이언트에서 분기해야 한다.
비즈니스 로직이 server function으로 새지 않도록 규칙을 둔다(AGENTS.md 참조).

## ADR-007 — 원문 페이지는 색인하지 않는다
**상태:** Accepted

**맥락:** Gutenberg 원문은 이미 수백 개 사이트에 존재한다. 신생 도메인이 중복 경쟁에서 이길 수 없다.

**결정:** 원문 전용 페이지는 `noindex, follow`. 번역 페이지가 canonical이자 색인 대상.
승인 커버리지가 임계값 미만인 챕터도 `noindex`.

**결과:** 크롤 예산이 고유 콘텐츠(번역문)에 집중된다. 임계값 수치는 미정(ADR 추가 필요).

## ADR-008 — 스토리지는 Cloudflare R2
**상태:** Accepted

**맥락:** Railway에는 오브젝트 스토리지가 없다. 원본 HTML 스냅샷을 보관해야 하고,
재파싱 때마다 다시 읽는다.

**결정:** Cloudflare R2. S3 호환이라 `aws-sdk-go-v2`를 그대로 쓴다.

**결과:** egress가 무료라 재파싱 비용 부담이 없다.

## ADR-009 — API는 스펙 우선 (OpenAPI)
**상태:** Accepted

**맥락:** Go 백엔드와 TS 프론트의 타입을 일치시켜야 한다.

**결정:** `openapi.yaml`이 단일 원본. `oapi-codegen`으로 Go 인터페이스를,
`orval`로 TS 클라이언트와 react-query 훅을 생성한다.

**결과:** 계약 변경이 양쪽에서 컴파일 에러로 드러난다. 생성 코드는 손으로 고치지 않는다.

## ADR-010 — LLM 번역 제안은 초기 범위에서 제외한다
**상태:** Accepted

**맥락:** 문단별 LLM 번역 제안을 검토했으나 초기 기획에서 뺐다.
개인 사용자는 LLM 요청 권한이 없다.

**결정:** 제안 생성은 전부 사람 손. `llm_suggestions` 테이블과 SSE 스트리밍,
레이트리밋, Anthropic SDK 의존성 모두 넣지 않는다.

**결과:** API가 평범한 JSON 엔드포인트만으로 구성된다.
`book_glossary`는 남긴다 — 여러 사용자가 같은 책을 번역할 때 인명·호칭 일관성 문제가
사람 번역에서도 동일하게 발생하며, 나중에 LLM을 붙일 때 프롬프트 프리픽스로 재사용된다.

---

## ADR-011 — 파서 검증을 스켈레톤보다 먼저 한다
**상태:** Accepted

**맥락:** Gutenberg HTML의 자동 분리 성공률이 설계를 바꾼다.
성공률이 높으면 수동 검토는 예외 처리 수준이면 되고, 낮으면 관리자 보정 UI가 핵심 기능이 되며
스키마에 보정 레이어가 필요해진다.

**결정:** `cmd/parsecheck` 스파이크로 실제 도서 15~20권을 추출해 리포트를 먼저 낸다.
그 결과를 보고 스켈레톤을 만든다.

**결과:** 스파이크의 `extractor.go`는 버리지 않고 `internal/parse/`로 이관한다.
원본 HTML은 커밋하지 않고 `corpus.json`(도서 ID)과 `golden/`(추출 결과 요약)만 남긴다.

## ADR-012 — 정규화에 `golang.org/x/text`를 쓴다
**상태:** Accepted

**맥락:** `stable_id` 정규화는 Unicode NFC가 필수다 (SPIKE_PARSER §5.7, 불변식 1).
스파이크 의존성 화이트리스트는 `goquery`와 `golang.org/x/net/html`뿐이었다.

**결정:** `golang.org/x/text/unicode/norm`을 추가한다. NFC를 손구현하지 않는다.

**결과:** `x/text`는 Go 확장 라이브러리다. 정규화 규칙은 그대로고, 의존성만 명세보다 하나 늘었다.

## ADR-013 — 파서 후처리: 앞부분 문단 보존, 빈 챕터, 제목 정리, 이미지 이니셜
**상태:** Accepted (2026-08-19)

**맥락:** 스파이크 공식 신뢰도는 22/22 자동이다. 그러나 `anchor-toc`는 목차 항목을 빈 챕터로 한 번 더 만들고,
첫 챕터 경계보다 앞에 있는 문단을 조용히 버리며, 삽화본 `h2`는 캡션을 장 제목에 붙이고,
이미지 드롭캡은 문단 첫 글자를 지운다. 상세는 `docs/PARSER_REPORT.md`.

> **검증 이력.** 이 초안은 두 번 정정됐다. 둘 다 리포트 수치를 코드 동작과 대조하다 드러났다.
> 1. **드롭캡 범위** — 초안은 5권(1342·345·98·1400·1661)을 대상으로 잡았다. 그것은
>    `dropcap`/`letra` **클래스가 등장한 문단 수**였고 평문 대조값이 아니었다. 텍스트 노드 드롭캡은
>    이미 정상 추출된다. 실제 유실은 이미지 이니셜뿐이고 1342 한 권 56문단이다.
>    초안대로 구현했다면 멀쩡한 4권에서 첫 글자가 중복됐다.
> 2. **문단 유실 원인** — 2차 초안은 "경계로 쓴 `<p>`의 본문을 버린다"로 적었다.
>    순회 로직을 재현해 분류한 결과 **유실 66건 중 65건은 첫 챕터 경계보다 앞에 있어서**
>    버려진 것이었다(`strategy_anchor_toc.go`의 `cur < 0` 분기). 경계로 쓰여 버려진 것은 1건뿐이다.
>    2차 초안대로 구현했다면 셰익스피어 1건만 고쳐졌다.

**결정:** 전략 점수 계산 뒤에 후처리를 둔다. 심각도 순이다.

1. **첫 챕터 경계 이전의 문단을 front-matter 챕터(idx 0)로 보존하고 `warnings`에 남긴다.**

   지금은 `cur < 0`이라 그냥 버려진다. 사라지는 양은 커버리지 1% 미만이라 신뢰도 공식에 잡히지 않고,
   관리자도 사라진 줄을 알아볼 수 없다.

   | 권 | 유실 `<p>` | 경계 이전 | 경계로 쓰임 | 사라진 내용 |
   |---|---|---|---|---|
   | 76 Huckleberry Finn | 51 | 51 | 0 | 목차형 `<p>` 다수 + 방언 설명 노트 |
   | 74 Tom Sawyer | 5 | 5 | 0 | **저자 서문 전체** |
   | 46 Christmas Carol | 4 | 4 | 0 | **저자 서문 전체** |
   | 345 Dracula | 4 | 4 | 0 | 표제지 |
   | 1524 Hamlet | 1 | 1 | 0 | 등장인물 목록 |
   | 205 Walden | 1 | 1 | 0 | 서두 인용 |
   | 100 Shakespeare | 1 | 0 | 1 | THE PROLOGUE 전문 |

   **전부 살리는 것도 답이 아니다.** 앞부분에는 살려야 할 것(74·46 서문, 1524 등장인물, 205 에피그래프)과
   버려야 할 것(76의 목차형 `<p>`, 345 표제지)이 섞여 있다.
   **판별을 파서가 떠맡지 않는다.** 일단 보존하고 경고를 남기면 관리자가 보고 즉시 판단할 수 있다.
   조용히 사라지는 지금이 최악이다. 76의 목차형 `<p>`는 별건으로 `ExcludeSelector` 보강을 검토한다.

   `section-chapter`도 같은 증상이 있다 — 첫 `section.chapter` 바깥의 문단이 수집되지 않는다
   (2542 인형의 집 등장인물 목록 187자). 후처리는 전략에 무관하게 적용한다.

   부수 효과: 앞부분 문단이 있는 권은 챕터가 하나씩 늘어난다.

2. **문단 0개 챕터 제거.**

   검증 완료. 정리 후 챕터 수가 실제 목차와 일치한다.

   | 권 | 현재 | 빈 챕터 | 정리 후 | 실제 |
   |---|---|---|---|---|
   | 84 Frankenstein | 56 | 28 | 28 | 편지 4 + 24장 |
   | 345 Dracula | 54 | 27 | 27 | 27장 |
   | 1524 Hamlet | 40 | 20 | 20 | 20 scene |
   | 46 Christmas Carol | 10 | 5 | 5 | Stave 5 |

   **1번과 충돌하지 않는다.** 빈 챕터를 만든 경계 요소는 전수 확인 결과 전부 `<a>` 앵커였다
   (84·345·46·74·1524·205). 1번이 `<p>`를 살려도 이 챕터들은 여전히 비어 있어 정상 제거된다.

   단, 1080(겸손한 제안)은 이 규칙만 적용하면 남는 챕터 제목이 `1729`가 된다.
   짧은 산문의 표제지 처리는 별건이며 이 ADR의 범위가 아니다.

3. **헤딩 정리 — 삽화 캡션과 페이지 번호.**

   1342의 `h2`는 캡션과 장 제목이 한 태그에 있어 `I hope Mr. Bingley will like it. CHAPTER II.`가 된다.
   `.caption` 제거로 해결된다.

   여기에 더해 **제목 전체가 페이지 번호인 경우**를 따로 다룬다. 1342의 챕터 `{ix}`(16문단),
   `{xxv}`(1문단)가 그렇다. 캡션 오염이 아니라 제목 자리에 페이지 마커만 있는 경우이고,
   내용은 실제 서문이라 챕터째 버릴 수도 없다. 제목만 비우거나 front-matter로 넘긴다.

4. **이미지 이니셜 복원 — `img alt`가 한 글자일 때만.**

   텍스트 노드 드롭캡(`.dropcap`/`.letra`)은 건드리지 않는다. 대상은 1342의 56문단이다.
   `alt`가 비었거나 여러 글자면 복원하지 않고 `warnings`에 남긴다.

5. **후처리 후 신뢰도를 재계산한다.**

   전략 **선택**은 후처리 전 원본 점수로 한다(전략별 성능 비교가 왜곡되지 않도록).
   그러나 저장되는 `confidence`와 golden 스냅샷은 **후처리 후 결과로 다시 계산한다.**
   그러지 않으면 0.85 자동 확정 게이트가 실제 저장물이 아닌 것을 근거로 판단한다.

   리포트 권고 4의 `emptyChapterRatio` 페널티는 이 항목에 종속된다 —
   후처리로 빈 챕터가 사라지면 그 페널티는 의미가 없어지므로, 재계산 도입 후 필요성을 다시 본다.

**결과:**

- 스키마 보정 레이어는 이 후처리 이후에도 남는 책만 대상으로 다시 판단한다.
  리포트 권고 2("지금은 넣지 말 것")가 그대로 유지된다.
- `stable_id` 등장 순서 부여(ADR-016)도 이 후처리 단계에서 함께 한다. 두 작업은 같이 구현한다.
- **golden 스냅샷 22권이 전부 바뀐다.** 챕터 수(§1·§2)와 문단 수(§1)가 달라지고,
  §5의 재계산으로 `confidence`까지 변한다. 갱신은 `make golden GOLDEN_UPDATE=1`이지만,
  **갱신 전에 `make parsecheck` 리포트로 눈 검증을 반드시 거친다.**
  "왜 바뀌었는지 확인하고 갱신"이 지켜지지 않으면 golden이 회귀 검증 기능을 잃는다.
- 1080(짧은 산문의 표제지)과 76의 목차형 `<p>` 제외는 이 ADR의 범위 밖으로 남는다.

## ADR-014 — 합본은 단권으로 수집하지 않는다
**상태:** Accepted (2026-08-19)

**맥락:** Gutenberg 100(셰익스피어 전집)은 파싱·메모리 모두 된다. 결과는 챕터 1684개, 절반이 빈 목차 항목이고
후처리 후에도 842챕터 39,354문단이다. 읽기·번역 UI가 성립하지 않는다.

초안에는 판정 기준이 없었다. `mega`는 스파이크 `corpus.json`의 메타데이터일 뿐 프로덕션에 존재하지 않으므로,
관리자가 카탈로그에서 100번을 고르면 막을 것이 없다.

**결정:** 합본을 **크기로 판정한다.** 코퍼스상 임계값은 깨끗하게 잡힌다.

| | 챕터 | 문단 |
|---|---|---|
| 100 Shakespeare | **1,684** | **39,354** |
| 2701 Moby Dick (챕터 2위) | 145 | 2,487 |
| 4300 Ulysses (문단 2위) | 21 | 7,064 |

- 기준: **챕터 200 초과 또는 문단 15,000 초과.** 어디에 그어도 100만 걸리고 나머지 21권은 안전하다.
- 판정 시점은 **파싱 후**다. 수집 전에는 크기를 알 수 없다.
- 초과 시 **하드 차단이 아니라 관리자 확인 큐로 보낸다.** 차단하면 나중에 작품 단위 분할을 붙일 때
  되돌리기 번거롭다. 나중에 넣는다면 작품 단위로 나눈 뒤에만 받는다.

**결과:** 100번은 수집은 되되 자동 확정되지 않는다. 임계값은 코퍼스 22권 기준이므로,
더 큰 합본이 들어오면 재검토한다. `corpus.json`의 `mega` 분류는 스파이크 기록으로만 남기고
프로덕션 판정에는 쓰지 않는다.

## ADR-015 — 희곡은 초기 지원 범위에서 제외한다
**상태:** Accepted (2026-08-19)

**맥락:** 스파이크는 희곡의 정답을 "깨끗한 실패"로 가정했다. 그런데 최신 `pg-images.html`에서는
실패하지 않았다 — 인형의 집은 ACT I–III(491/434/385문단), 햄릿은 후처리 후 20 scene으로
깨끗하게 갈리고 대사는 `p`다. 즉 **파서가 못 해서 빼는 것이 아니다.**

남는 것은 제품 질문이었다. 번역 단위를 act/scene + 대사 문단으로 둘 것인가,
대사 문단에 화자명이 포함되는 것(`"LAERTES. What ceremony else?"`)을 어떻게 다룰 것인가.

**결정:** 희곡을 **초기 지원 범위에서 뺀다.** 추후 반영 후보로 남긴다.

**구현 방식 — 코드 게이트를 넣지 않는다.**

장르 자동 판별은 ADR-014의 크기 판정과 다르다. 챕터 200·문단 15,000처럼 코퍼스에서
깨끗하게 갈리는 임계값이 없다. `PARSER_REPORT.md` §6이 적었듯 장르 감지는
"화자 짧은 문단, ACT/SCENE" 같은 별도 휴리스틱이 필요하고, 잘못 만들면
**산문을 희곡으로 오판해 막는다.** 없는 게이트보다 틀린 게이트가 나쁘다.

따라서 제외는 **도서 선정 단계의 운영 정책**이다. 관리자가 희곡을 고르지 않는다.

**검증 코퍼스는 그대로 둔다.** `corpus.json`의 2542(인형의 집)·1524(햄릿)는
파서 검증 fixture이고 구조 다양성 확보가 목적이다. **지우지 말 것.**
이 결정은 프로덕션 도서 선정에 관한 것이지 테스트 데이터에 관한 것이 아니다.

**결과:**

- 파서 작업이 필요 없다. 나중에 넣기로 하면 **도서를 추가하기만 하면 된다.**
  진입 비용이 낮게 유지되므로 서두를 이유가 없다.
- 대사 중복 문제(햄릿 4.9%)는 ADR-016이 이미 해결했다. 나중에 희곡을 넣어도 이 축은 안전하다.
- 다시 검토할 때 남는 질문 두 개:
  번역 단위를 act/scene 챕터 + 대사 문단으로 둘 것인가,
  대사에 붙은 화자명을 번역 대상에 포함할 것인가.
- 운문은 이 코퍼스로 검증되지 않았다(1727은 Butler **산문** 번역이다).
  운문 지원은 별건이며 검증부터 다시 해야 한다.

## ADR-016 — 반복 본문의 `stable_id` 충돌은 등장 순서로 분리한다
**상태:** Accepted (2026-08-19). ADR-004를 보완한다 — 뒤집지 않는다.

**맥락:** ADR-004는 `stable_id = sha256(정규화 본문)[:16]`으로 정의했고,
`paragraph_translations`의 PK는 `(project_id, paragraph_stable_id)`다(ADR-005).
해시 입력이 본문뿐이므로 **본문이 같은 문단은 책의 서로 다른 위치에 있어도 번역 행 하나를 공유한다.**
제안(`translation_proposals`)도 같은 키를 쓰므로 제안·검수·읽기 화면이 모두 함께 묶인다.

스파이크 재검증에서 규모가 확인됐다. 파서의 더블카운팅이 아니라 원문에 실제로 반복되는 문장이다
(발생 위치가 전부 다른 챕터·인덱스).

| 권 | 총 문단 | 자리를 잃는 문단 | 비율 |
|---|---|---|---|
| 100 Shakespeare | 39,354 | 2,136 | 5.4% |
| 1524 Hamlet | 1,376 | 67 | 4.9% |
| 345 Dracula | 1,945 | 64 | 3.3% |
| 1661 Sherlock Holmes | 2,523 | 42 | 1.7% |
| 98 A Tale of Two Cities | 3,259 | 53 | 1.6% |
| 4300 Ulysses | 7,064 | 72 | 1.0% |

22권 중 6권은 중복이 0이다. 중복의 거의 전부가 60자 이하 짧은 대사다.

**결정:** 같은 본문의 **첫 등장은 지금과 동일하게** `sha256(text)`를 쓰고,
2번째 이후만 등장 순서를 붙인다.

```
n = 1  →  stable_id = sha256(normalized)[:16]              (현행과 완전히 동일)
n ≥ 2  →  stable_id = sha256(normalized + "#" + n)[:16]
```

순서 부여는 **파서 후처리 단계**에서 한다(ADR-013 후처리 뒤, 챕터·문단 순서가 확정된 시점).
`Normalize`에는 넣지 않는다 — 앞선 문단을 알아야 하므로 순수 함수가 깨지기 때문이다
(SPIKE_PARSER §5.7의 "정규화 함수는 순수 함수여야 한다"를 유지).

### 왜 안 C인가 — 검토한 세 안

**안 A(현행 유지, 충돌 허용) — 기각.** 제품 결정이다.
영어 `"Yes."`는 화자와 상대에 따라 `"네."` / `"그래."` / `"예, 그렇습니다."`로 달라져야 하는데,
행이 하나뿐이면 **같은 원문이 나오는 모든 자리에 같은 존댓말이 강제된다.**
번역자가 화자별로 다르게 옮길 방법이 아예 없다.
용어 일관성은 `book_glossary`가 담당하므로(ADR-010), 대사까지 강제로 통일할 이유가 없다.

**안 B(위치를 해시에 포함, `sha256(chapter_idx + para_idx + text)`) — 기각.**
충돌은 사라지지만 **ADR-004의 존재 이유를 스스로 무효화한다.**
ADR-004는 "재파싱하면 문단 행 ID가 밀린다"를 풀려고 만들어졌는데,
안 B는 위치를 해시에 넣어 "밀리면 깨진다"를 되살린다. `paragraphs.id`를 참조하는 것과 실질적으로 같고,
FK 무결성만 포기하고 얻는 것이 없다.

이건 이론이 아니라 당장 닥친다. **ADR-013(빈 챕터 제거)을 적용했을 때 기존 id 생존율**을
코퍼스 22권으로 시뮬레이션한 결과:

| | 안 B 생존 | 안 C 생존 |
|---|---|---|
| **22권 평균** | **32.5%** | **100.0%** |
| 84 Frankenstein (빈 챕터 28) | 0.3% | 100% |
| 345 Dracula (27) | 0.1% | 100% |
| 100 Shakespeare (842) | 0.0% | 100% |
| 1524 Hamlet (20) | 0.0% | 100% |
| 76 Huckleberry Finn (44) | 0.0% | 100% |
| 1400 Great Expectations (0) | 100% | 100% |

15권에서 거의 전멸한다. 100% 생존한 7권은 빈 챕터가 0이라 아무것도 밀리지 않은 책들뿐이다 —
즉 안 B가 살아남는 조건은 "파서 결과가 하나도 안 바뀐 경우"다.
챕터 하나만 지워져도 뒤따르는 모든 챕터의 `chapter_idx`가 밀리고, 그 안 모든 문단의 id가 바뀐다.
지역적 변경이 전역적 id 변경으로 증폭된다.

부작용이 하나 더 있다. 안 B에서는 본문이 한 글자도 안 바뀌어도 위치만 밀리면 해시가 달라지므로,
ADR-004의 revision 전환 규칙에서 **"해시 일치 → 자동 승계"가 사실상 발동하지 않고**
전부 관리자 확인 큐로 쏟아진다. 위대한 유산이면 3,833건, 셰익스피어면 39,354건이다.
큐가 예외 처리용이 아니라 주 작업이 된다.

**안 C(반복분에만 등장 순서) — 채택.**
해시 입력이 본문뿐이라 위치가 아무리 밀려도 본문이 같으면 id가 같다. 위 시뮬레이션에서 100% 생존한다.
첫 등장의 id를 바꾸지 않으므로 **중복 없는 문단(대다수)과 중복 0인 6권은 영향이 전혀 없다.**
충돌 위험은 "같은 본문을 가진 문단들" 안으로 갇힌다.

**결과:**

- 문단당 확정본 1개(불변식 2)와 재파싱 안전성(불변식 1)을 둘 다 유지한다.
- `paragraph_translations` / `translation_proposals`의 스키마는 바뀌지 않는다.
  `stable_id`를 만드는 규칙만 바뀐다.
- **남는 위험:** 같은 본문의 반복 사이에 새 반복이 끼어들면 뒤쪽 순서가 밀린다.
  드라큘라 `"Jonathan Harker's Journal."` 9회 중 앞쪽에 하나가 새로 잡히면 뒤 8개가 +1 된다.
  영향이 그 텍스트에만 갇히고 건수도 작아서, ADR-004의 "유사 → 관리자 확인 큐"가 받아낸다.
- 본문 자체가 바뀌면(예: ADR-013의 이미지 이니셜 복원 56문단) 어떤 방식으로도 id가 바뀐다.
  이는 ADR-004가 설계상 받아내기로 한 부분이다.
- 구현: `internal/parse/postprocess.go`의 `assignOccurrenceIDs`. `Normalize`는 순수 함수로 그대로다.

## ADR-017 — 마이그레이션은 goose, DB 드라이버는 pgx/v5
**상태:** Accepted (2026-08-19)

**맥락:** `ARCHITECTURE.md`와 `AGENTS.md`는 `internal/db/migrations/`에 순번 SQL을 두고
`make migrate`로 적용한다고만 정했다. **러너는 미지정이었다.**
sqlc가 생성할 코드의 드라이버도 정해지지 않았다. 둘 다 새 의존성이라 결정이 필요하다.

**결정:**

- 마이그레이션 러너는 **`github.com/pressly/goose/v3`**. 라이브러리로 임베드해
  `make migrate`를 `go run`으로 처리한다.
- DB 드라이버는 **`github.com/jackc/pgx/v5`**. sqlc는 `pgx/v5` 타입으로 생성한다.
- sqlc 자체는 빌드 타임 도구다. 런타임 의존성이 아니며 `make doctor`에서 존재만 확인한다.

**대안과 기각 사유:**

- **golang-migrate** — 가장 널리 쓰이지만 CLI 설치가 전제이고 `make doctor` 확인 항목이 하나 는다.
  goose는 라이브러리 임베드로 별도 바이너리 없이 끝난다.
- **atlas** — 선언적 스키마 관리가 강력하나 이 규모에 무겁고,
  "순번 SQL 파일을 직접 작성하고 적용된 파일은 수정하지 않는다"는 기존 규약과 결이 다르다.
- **러너 없이 psql** — 의존성은 0이지만 적용 이력 추적을 직접 만들게 되고, 결국 러너를 재발명한다.

**결과:**

- 개발자가 설치할 바이너리는 sqlc 하나로 유지된다. goose는 `go.mod`에 들어간다.
- 마이그레이션 파일명은 goose 규약(`NNNNN_설명.sql`, `-- +goose Up` / `-- +goose Down`)을 따른다.
  기존 규약의 "순번 SQL"과 충돌하지 않는다.
- River를 붙일 때 River 자체 마이그레이션이 따로 온다. 두 러너가 공존하게 되며,
  적용 순서(goose 먼저 → River)를 그때 명시한다.

## ADR-018 — HTTP 라우터는 chi
**상태:** Accepted (2026-08-19)

**맥락:** 라우터가 결정된 적이 없다. 문서 전체에 근거가 두 개뿐이었다 —
`ARCHITECTURE.md`·`CONVENTIONS.md`의 `srv := &http.Server{...}` 조각(표준 `net/http`)과
ADR-009의 "oapi-codegen으로 Go 서버 인터페이스를 생성한다".

**지금 정해야 하는 이유:** oapi-codegen은 **대상 라우터별로 다른 코드를 생성한다**
(`chi-server`, `std-http-server`, `echo-server`, `gin-server` …).
설정 파일에 대상을 적어야 하므로 `openapi.yaml`을 만드는 시점에 이미 정해져 있어야 한다.

**결정:**

- 라우터는 **`github.com/go-chi/chi/v5`**.
- oapi-codegen 생성 대상은 **`chi-server`**.
- 핸들러는 `http.HandlerFunc` 시그니처를 유지한다. chi 고유 타입을 핸들러 인자로 쓰지 않는다.
- 미들웨어는 표준 `http.Handler` 래퍼만 쓴다.

**대안과 기각 사유:**

- **표준 `net/http` (`std-http-server`)** — 의존성이 0이고 Go 1.22+ `ServeMux`의
  메서드·와일드카드 라우팅으로 라우팅만 보면 충분하다(이 프로젝트는 1.26.6).
  기각 이유는 라우팅이 아니라 미들웨어다. 세션 인증, 관리자·검수자 권한 분리,
  요청 로깅(`log/slog`), 패닉 복구, 요청 ID를 전부 직접 조립해야 한다.
  제품 코드가 아닌 곳에 시간을 쓴다.
- **echo / gin / fiber** — 자체 컨텍스트 타입을 쓴다.
  "`context.Context`는 항상 첫 인자", "외부 I/O는 인터페이스 뒤에"라는 기존 규약과 결이 다르고,
  핸들러가 프레임워크에 묶여 나중에 갈아타기 어렵다.

**결과:**

- **잠기지 않는다.** chi는 프레임워크가 아니라 라우터 + 미들웨어 모음이고 핸들러 시그니처가
  표준과 같다. 나중에 표준 `ServeMux`로 옮겨도 핸들러는 손대지 않는다.
  되돌리기 쉬운 결정이므로 여기에 더 시간을 쓰지 않는다.
- `go.mod` 런타임 의존성은 goquery / x/text / pgx / goose / chi 다섯이 된다.
- `AGENTS.md` 기술 스택 표의 백엔드 행에 반영한다.

## ADR-019 — 패키지 매니저는 pnpm, Node 패키지는 `web/` 하나
**상태:** Accepted (2026-08-19)

**맥락:** 슬라이스 1(골격)에 이미 프론트엔드 작업이 들어 있다 —
`web/`의 TanStack Start SSR과 `make generate`의 orval 실행.
**패키지 매니저가 정해지지 않으면 슬라이스 1을 시작할 수 없다.**
Go 쪽은 ADR-017·018로 막아뒀는데 TS 쪽만 비어 있었다.

**결정:**

- 패키지 매니저는 **pnpm**. 버전은 `package.json`의 `packageManager` 필드로 고정하고
  corepack으로 활성화한다.
- **Node 패키지는 `web/` 하나만 둔다. 루트 `package.json`을 만들지 않는다.**
- **orval은 `web/`의 devDependency**로 두고 설정에서 `../openapi.yaml`을 참조한다.
- `make generate`는 Makefile에서 `web/` 안의 스크립트를 호출한다.
  **Makefile이 유일한 진입점**이라는 규약은 그대로다.

**대안과 기각 사유:**

- **npm** — Node에 내장돼 추가 설치가 없다. "개발자가 설치할 바이너리를 늘리지 않는다"는
  ADR-017의 논리와 일관된다. 그럼에도 pnpm을 고른 것은 **엄격한 `node_modules` 구조** 때문이다.
  `package.json`에 없는 패키지를 import해도 동작해버리는 사고(phantom dependency)를 막는다.
  이 프로젝트는 생성 코드가 많아 의존 관계가 흐려지기 쉽다. corepack으로 설치 부담도 작다.
- **bun** — 가장 빠르지만 TanStack Start·Vite·orval 조합의 검증 사례가 상대적으로 적다.
  이 슬라이스의 목적이 "도구 체인이 실제로 도는가"인데, 변수를 늘리는 선택이다.

**결과:**

- lockfile은 `web/pnpm-lock.yaml` 하나다. 저장소에 Node 패키지가 둘이 되지 않는다.
- `make doctor`에 pnpm 확인 항목이 하나 는다. **함께 갱신할 것.**
- Railway `web` 서비스 빌드가 pnpm을 쓰도록 설정해야 한다. 배포 슬라이스에서 확인한다.
- 루트에 `package.json`이 없으므로 TS 도구를 저장소 전역에 두려면 이 결정을 먼저 뒤집어야 한다.

## ADR-020 — 빌드 타임 코드 생성기는 `go.mod`의 tool 디렉티브로 고정한다
**상태:** Accepted (2026-08-19). ADR-017의 sqlc 관련 서술을 보완한다 — 러너·드라이버 결정은 그대로다.

**맥락:** 슬라이스 1에서 `make generate`를 되살리려면 sqlc와 oapi-codegen이 실제로 실행돼야 한다.
ADR-017은 "sqlc 자체는 빌드 타임 도구다. 런타임 의존성이 아니며 `make doctor`에서 존재만 확인한다"고
적었고, 이는 설치된 바이너리를 전제한다. oapi-codegen은 아예 정해진 적이 없다.

전제를 그대로 따르면 개발자가 설치할 바이너리가 둘(`brew install sqlc`, `go install oapi-codegen`)이 된다.
이는 ADR-017이 golang-migrate를 기각할 때 쓴 논리("CLI 설치가 전제이고 `make doctor` 확인 항목이 하나 는다",
"개발자가 설치할 바이너리를 늘리지 않는다")와 정면으로 어긋난다.

**결정:** Go 1.24+의 `tool` 디렉티브로 둘 다 `go.mod`에 고정한다.

```
tool (
	github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen
	github.com/sqlc-dev/sqlc/cmd/sqlc
)
```

Makefile은 `go tool sqlc` / `go tool oapi-codegen`으로 부른다.
`make doctor`는 두 도구를 계속 확인하되, 확인 대상이 PATH의 바이너리가 아니라 tool 디렉티브다.

**대안과 기각 사유:**

- **brew / `go install`로 바이너리 설치** — ADR-017의 전제이지만 버전이 저장소에 박히지 않는다.
  생성 코드는 커밋되므로, 개발자마다 생성기 버전이 다르면 `make generate`가 diff를 만들어낸다.
  `go install`은 `GOPATH/bin`이 PATH에 없으면 조용히 실패한다.
- **생성 코드를 커밋하지 않고 빌드 때마다 생성** — 생성기 부재가 빌드 실패로 바로 드러나지만,
  "생성 코드는 커밋한다"는 기존 `.gitignore` 방침을 뒤집어야 한다. 이 슬라이스의 범위가 아니다.

**결과:**

- 개발자가 설치할 바이너리는 **0개**가 된다. corepack으로 pnpm을 켜는 것만 남는다.
- 생성기 버전이 `go.mod`에 박히므로 `make generate` 결과가 사람마다 같다.
  현재 sqlc v1.31.1 / oapi-codegen v2.8.0.
- `go.mod`의 indirect 블록이 커진다. **런타임 의존성은 늘지 않는다** —
  tool 디렉티브의 패키지는 `cmd/api`·`cmd/worker` 바이너리에 들어가지 않는다.
- 도구 버전을 올릴 때는 `go get -tool <path>@<version>` 뒤에 `make generate`로 diff를 확인한다.

## ADR-021 — `oapi-codegen/runtime`은 생성 코드가 강제하는 런타임 의존성이다
**상태:** Accepted (2026-08-19). ADR-009의 귀결이며 새 선택이 아니다.

**맥락:** 읽기 경로 슬라이스에서 첫 경로 파라미터 엔드포인트
(`GET /books/{gutenbergId}/chapters/{idx}`)가 생겼다. oapi-codegen이 생성한 chi 바인딩이
`runtime.BindStyledParameterWithOptions`를 부르므로 `github.com/oapi-codegen/runtime`이
`go.mod`에 들어간다. 헬스체크 하나뿐일 때는 파라미터가 없어 드러나지 않았다.

슬라이스 명세는 "의존성을 새로 추가하지 않는다. 필요하면 `Proposed` ADR로 남기고 확인할 것"이라고
적었다. 그래서 남긴다 — ADR-012(`x/text`)와 같은 성격의 기록이다.

**결정:** 추가한다. 선택지가 없다.

- oapi-codegen에는 이 런타임을 쓰지 않는 생성 모드가 없다. 경로·쿼리 파라미터 바인딩이
  전부 이 패키지를 거친다.
- 손으로 파라미터를 파싱하면 **생성 코드를 손으로 고치지 말라**는 규약(작업 규칙 4)을 어긴다.
- 라우터를 바꿔도(chi → 표준 `ServeMux`) 이 의존성은 남는다. 라우터가 아니라 생성기에 딸린 것이다.

**결과:**

- 런타임 직접 의존성이 여섯이 된다: goquery / x/text / pgx / goose / chi / oapi-codegen-runtime.
- ADR-009를 뒤집지 않는 한 제거할 수 없다. 스펙 우선을 포기하면 사라지지만 그럴 이유가 없다.
- 앞으로 파라미터가 있는 엔드포인트를 추가할 때 이 항목을 다시 열 필요는 없다.

## ADR-022 — 마이그레이션은 goose 먼저, River 나중
**상태:** Accepted (2026-08-19). ADR-017이 "그때 명시한다"고 남겨 둔 항목이다.

**맥락:** ADR-017은 러너를 goose로 정하면서 이렇게 적었다 —
"River를 붙일 때 River 자체 마이그레이션이 따로 온다. 두 러너가 공존하게 되며,
적용 순서(goose 먼저 → River)를 그때 명시한다."

이제 River를 붙였으므로 명시한다. 러너가 둘이라는 것 자체는 피할 수 없다:
River는 자기 테이블(`river_job`, `river_leader`, `river_queue` 등)을 자기 마이그레이터로 관리하고,
그 스키마는 River 버전에 묶여 있다. goose 파일로 베껴 쓰면 River를 올릴 때마다 손으로 따라가야 한다.

**결정:** `make migrate`는 **goose를 전부 적용한 뒤 River 마이그레이터를 돌린다.**
둘 다 `tools/migrate` 한 진입점에서 순서대로 실행한다.

**왜 이 순서인가:**

- goose가 애플리케이션 스키마의 단일 원본이다. `books` 같은 도메인 테이블이 없는데
  잡 테이블부터 만들면, 잡이 참조할 대상이 없는 중간 상태가 생긴다.
- River 마이그레이터는 자기 테이블만 본다. goose가 만든 것에 의존하지 않으므로
  나중에 돌아도 안전하다. 반대 순서는 안전하지 않다.
- 두 러너의 이력 테이블이 다르다(`goose_db_version` vs `river_migration`). 서로 간섭하지 않는다.

**대안과 기각 사유:**

- **River 스키마를 goose 파일로 옮겨 적기** — 러너가 하나로 준다.
  기각한 이유는 River 업그레이드 때마다 스키마 diff를 손으로 따라가야 하고,
  "적용된 마이그레이션 파일은 수정하지 않는다"는 규약과 맞물려 파일이 계속 쌓인다.
  버전 불일치를 알아채는 방법도 없다.
- **각 서비스가 기동할 때 알아서 마이그레이션** — 인스턴스를 여러 개 띄우면 경합한다.
  Railway 배포 교체 중에는 구/신 버전이 동시에 뜬다.

**결과:**

- `make migrate`가 유일한 진입점이다. 두 러너를 따로 부르지 않는다.
- **sqlc는 goose 마이그레이션만 읽는다** (`sqlc.yaml`의 `schema`). River 테이블은
  sqlc 모델에 잡히지 않으며 그게 맞다 — 잡 테이블은 River가 다룬다.
- 배포 파이프라인에서도 `make migrate` 한 번이면 된다. 순서를 배포 스크립트가 알 필요가 없다.

## ADR-023 — 챕터 색인 임계값은 승인 커버리지 80%
**상태:** Accepted (2026-08-19). ADR-007이 "수치 미정"으로 남긴 항목을 채운다.

**맥락:** ADR-007은 "승인 커버리지가 임계값 미만인 챕터도 `noindex`"라고 정했지만
수치는 비워 뒀다. 번역 슬라이스에서 읽기 화면이 실제로 색인 메타를 내보내야 하므로 정한다.

**결정:** `승인 문단 수 / 챕터 전체 문단 수 >= 0.80`이면 `index, follow`, 아니면 `noindex, follow`.

**왜 80인가:**

- 60%는 페이지의 40%가 Gutenberg 원문이다. ADR-007이 피하려던 중복 콘텐츠 비중이
  그대로 남아, 색인시켜도 순위 경쟁에서 이길 근거가 없다.
- 95~100%는 안전하지만 ADR-007 자신이 경계한 지점이다 —
  "승인률 100%를 기다리면 아무 책도 공개하지 못한다".
  초기에는 색인되는 페이지가 거의 없어 SEO 가설 자체를 검증할 수 없다.
- 80%면 페이지의 대부분이 고유 콘텐츠이고, 한 챕터를 완역하지 않아도 공개가 열린다.

**결과:**

- 임계값은 코드 상수가 아니라 설정값으로 둔다. 색인 결과를 보고 조정할 수 있어야 한다.
  기본값 0.80. 바꾸면 이 ADR을 갱신한다.
- 프로젝트 전체 공개 기준과는 별개다. 이 수치는 **챕터 단위 색인**에만 쓴다.
- 미확정 문단은 원문으로 노출한다. 색인 여부와 무관하게 부분 공개는 허용한다.

## ADR-024 — 같은 문단의 승인은 자문 잠금으로 직렬화한다
**상태:** Accepted (2026-08-19). ADR-005를 보완한다 — 뒤집지 않는다.

**맥락:** ADR-005와 `ARCHITECTURE.md` 불변식 3은 승인 트랜잭션의 2단계
`WHERE id=$4 AND status='pending'`이 동시 승인을 막는다고 적었다.
번역 슬라이스에서 그것을 처음 시험했고, **막지 못하는 경우가 있었다.**

`status='pending'` 조건은 **같은 제안**을 두 검수자가 동시에 승인하는 것만 막는다.
같은 문단의 **서로 다른** 제안을 동시에 승인하면 다르게 흐른다:

```
T1: 1단계 supersede → 확정본 없음, 아무것도 안 함
T2: 1단계 supersede → 확정본 없음, 아무것도 안 함   (T1이 아직 커밋 전)
T1: 2단계 P1 승인 (pending이므로 통과)
T2: 2단계 P2 승인 (pending이므로 통과)
T1: 3단계 확정본 INSERT
T2: 3단계 확정본 UPSERT — PK 충돌로 대기했다가 덮어씀
```

결과: 확정본은 1행이다(복합 PK가 지킨다). 그러나 **`approved` 제안이 2개 남는다.**
확정본이 가리키지 않는 제안이 승인 상태로 떠 있고, 검수 화면과 이력이 거짓말을 한다.

**재현했다.** 서로 다른 제안 둘을 동시에 승인하는 것을 40라운드 반복하니
거의 전부에서 `approved=2, 확정본=1`이 나왔다.
**단발 테스트로는 통과한다** — 처음에 그렇게 놓쳤다. 인터리빙이 맞아떨어져야 드러난다.

**결정:** 승인 트랜잭션 맨 앞에서 `(project_id, paragraph_stable_id)`에 대해
`pg_advisory_xact_lock`을 잡는다. 트랜잭션이 끝나면 자동 해제된다.

```sql
SELECT pg_advisory_xact_lock(hashtextextended(project_key || ':' || stable_id, 0));
```

**ARCHITECTURE의 3단계는 그대로 둔다.** 순서를 바꾸지 않고 앞에 잠금만 더한다.

**대안과 기각 사유:**

- **`SELECT ... FOR UPDATE`로 확정본 행 잠그기** — 첫 승인 때는 행이 없어 잠글 것이 없다.
  이 버그가 정확히 "확정본이 아직 없을 때" 나므로 아무것도 막지 못한다.
- **3단계(확정본 UPSERT)를 1단계보다 먼저 하고 그 뒤에 supersede** — 실제로 동작한다.
  PK 충돌로 두 번째 트랜잭션이 대기하므로, 그 뒤의 supersede는 첫 번째의 승인을 보게 된다.
  기각한 이유는 **문장 순서에 correctness가 걸린다**는 것이다. 나중에 누가 읽기 좋게
  순서를 되돌리면 조용히 깨지고, 단발 테스트로는 드러나지 않는다.
  자문 잠금은 의도가 코드에 드러난다.
- **직렬화 격리 수준(SERIALIZABLE)** — 맞는 답이지만 승인 외의 모든 트랜잭션에도
  재시도 처리를 넣어야 한다. 문제가 한 지점에 갇혀 있는데 전역 비용을 치를 이유가 없다.

**결과:**

- 승인은 문단 단위로 직렬화된다. 서로 다른 문단은 여전히 병렬이다.
  해시 충돌로 무관한 두 문단이 가끔 직렬화될 수 있으나 대기가 짧아 문제되지 않는다.
- **반복 테스트를 유지한다** (`TestConcurrentApprovalStress`).
  단발로는 잡히지 않는 버그라 라운드 수를 줄이지 말 것.
- 불변식 2(문단당 확정본 1개)는 여전히 스키마가 지킨다. 이 잠금이 지키는 것은
  **제안 상태와 확정본의 일관성**이고, 그것은 여러 행에 걸쳐 있어 제약으로 표현할 수 없다.

## ADR-025 — 인라인 쪽번호를 본문에서 제거하고, 이미지 제목을 alt에서 복원한다
**상태:** Accepted (2026-08-19). ADR-013을 보완한다 — 뒤집지 않는다.

**맥락:** 읽기 화면을 눈으로 보다 1342의 본문에 `{xi}` 같은 조각이 문장 한가운데 박혀 있는 것을 발견했다.

```
"I do not know whether,{xi} this combination of the fresh and vigorous..."
"her own comparison to the art of a miniature{xv} painter."
```

원문의 종이책 쪽번호 앵커다. 문단 **안에** 인라인으로 들어 있다.

```html
<span class="pagenum"><a id="page_xxiv">{xxiv}</a></span>
```

`ExcludeSelector`는 `Closest`로 **조상**만 보므로 자손인 이것을 걸러내지 못했다.
**1342에서만 474문단**이 오염됐고, 코퍼스 22권 중 이 표기를 쓰는 책은 1342 하나다.
그래서 스파이크에서 눈에 띄지 않았고 `PARSER_REPORT.md`에도 없다.

ADR-013 §3은 **제목**이 통째로 쪽번호인 경우(`{ix}`, `{xxv}`)를 다뤘다.
같은 앵커였는데 제목만 보고 본문은 놓친 것이다.

**이게 미관 문제가 아닌 이유:** `{xi}`가 `stable_id` 해시 입력에 들어가 있다.
나중에 벗겨내면 474문단의 id가 전부 바뀌고, 번역이 붙어 있었다면 전부 고아가 된다.
ADR-004가 "유일하게 되돌리기 어려운 실수"라고 지목한 지점이다.
**번역이 쌓이기 전에 고치는 것이 요점이다.**

**결정:**

1. **문단 텍스트에서 `.pagenum`을 제거한다.** `InlineNoiseSelector` 상수로 둔다.
   HTML 조각은 손대지 않는다 — 이미지 이니셜 복원(ADR-013 §4)이 원본을 봐야 한다.
2. **제목이 비면 헤딩 안 `img alt`에서 읽는다.**
   1342의 `h2` 65개 중 63개가 `<img>`를 갖고, 두 개는 제목이 alt에만 있다:
   `alt="PREFACE."`, `alt="List of Illustrations."`.
   ADR-013 §3이 "제목만 비우거나 front-matter로 넘긴다"고 한 자리인데,
   **비울 필요가 없었다 — 제목은 있었고 이미지 안에 있었을 뿐이다.**
   서문 16문단이 "제목 없음"으로 남아 있던 것이 이 때문이다.
3. `parse.Version`을 `2026-08-19.2`로 올린다. 같은 날 두 번 바뀔 수 있으므로 순번을 붙인다.

**alt 복원 범위가 ADR-013 §4와 다른 이유:** 저기서는 드롭캡 **한 글자**만 복원하고
여러 글자면 경고만 남긴다. 여기서는 alt 전체가 제목이므로 그대로 쓴다. 목적이 다르다.

**측정 결과 — 승계 도구의 첫 실전 사용:**

| | 저장 문단 | 일치 | 승계율 | 소실 |
|---|---|---|---|---|
| 1342 Pride and Prejudice | 2,139 | 1,665 | **77.8%** | 474 |
| 나머지 20권 | 34,986 | 34,986 | 100% | 0 |
| 합계 | 37,125 | 36,651 | 98.7% | 474 |

소실 474는 오염 문단 수와 정확히 일치한다. 번역이 붙어 있었다면 그만큼 고아가 됐을 것이다.
`SLICE_READ_PATH.md` §4.4가 "파서를 고친 뒤 돌려 보는 것이 사용법"이라고 적은 그대로다.

**결과:**

- 챕터 64 → 63, 문단 2,139 → 2,131. 사라진 8문단은 내용이 `{1}`, `{6}`처럼
  쪽번호뿐이던 것들이고 전수 확인했다. 남은 한 챕터는 문단이 0개가 되어
  ADR-013 §2 규칙대로 제거됐다(삽화 목록이며 본문이 없다).
- `coverage`가 0.9895 → 0.9862로 내려간다. 본문 길이 분모는 마커를 포함한 채인데
  추출 텍스트에서만 빠졌기 때문이다. 내용이 사라진 것이 아니다.
- **선택자는 `.pagenum` 하나뿐이다.** `.pageno` 같은 변형은 코퍼스에 나타나지 않았고,
  근거 없이 넓히지 않는다 — 없는 규칙보다 틀린 규칙이 나쁘다 (ADR-015).
  다른 표기를 쓰는 책이 들어오면 그때 근거와 함께 추가한다.

## ADR-026 — 브라우저의 교차 출처 호출은 출처 허용목록으로 받는다
**상태:** Accepted (2026-08-19)

**맥락:** 읽기 화면에서 다음 챕터를 누르면 `Failed to fetch`가 났다.

첫 진입은 SSR이라 **서버가** API를 부르고, 그 뒤 라우터 이동은 **브라우저가** 직접 부른다.
웹과 API는 출처가 다르므로(로컬 `:3100` / `:8080`) 후자는 교차 출처 요청이다.
Go API에 CORS 미들웨어가 없어 브라우저가 응답을 버렸고, `OPTIONS`는 405였다.

**로컬만의 문제가 아니다.** `ARCHITECTURE.md` 불변식 4가
"SSR 서버가 API를 호출할 때는 `서비스명.railway.internal`을 쓴다. 브라우저는 공개 도메인을 쓴다"고
정했으므로, 프로덕션에서도 브라우저 → API는 언제나 교차 출처다.

**결정:** `github.com/go-chi/cors`를 미들웨어로 붙이고,
허용 출처를 `CORS_ALLOWED_ORIGINS`(쉼표 구분)로 받는다. 없으면 기동 실패.

- **와일드카드(`*`)를 쓰지 않는다.** 클라이언트가 `credentials: 'include'`로 보내므로
  규격상 `*`가 허용되지 않고, 허용해서도 안 된다 —
  아무 사이트나 사용자 세션으로 이 API를 부르게 된다.
- 허용 헤더에 `X-Admin-Token`, `X-User-Handle`을 넣는다.
  커스텀 헤더는 preflight 대상이라 빠뜨리면 `OPTIONS`에서 막힌다.
- 허용 메서드는 `GET`, `POST`, `OPTIONS`뿐이다. 지금 계약에 다른 메서드가 없다.

**대안과 기각 사유:**

- **직접 구현** — 의존성이 늘지 않는다. 기각한 이유는 CORS가 조용히 틀리기 쉽기 때문이다.
  출처 반사, `Vary` 누락, preflight 캐시, credentials 조합에서 하나만 어긋나도
  보안 구멍이거나 디버깅하기 어려운 실패가 된다.
  ADR-018이 표준 `net/http`를 기각할 때 쓴 논리와 같다 — 제품 코드가 아닌 곳에 시간을 쓰지 않는다.
- **Vite 개발 서버 프록시로 같은 출처 만들기** — 로컬에서는 되지만 프로덕션에서 안 된다.
  개발과 프로덕션의 요청 경로가 달라져, 로컬에서 통과한 것이 배포 후 깨진다.
- **브라우저도 SSR을 거치게 하기(server function 경유)** — 비즈니스 로직이
  server function으로 새는 길이고 ADR-006이 금지한다.

**결과:**

- 런타임 직접 의존성이 일곱이 된다. `go-chi/cors`는 chi 계열이라 미들웨어 시그니처가 표준과 같다.
- **LAN이나 Tailscale로 접속하려면 그 출처도 목록에 넣어야 한다.**
  `make run-web-lan`을 쓸 때 `CORS_ALLOWED_ORIGINS`에 `http://192.168.x.x:3100`을 추가한다.
  잊으면 첫 화면만 뜨고 챕터 이동이 막힌다 — 증상이 이 ADR을 만든 그것과 같다.
- 세션 인증(슬라이스 5)이 붙으면 쿠키가 이 경로로 오간다.
  `AllowCredentials: true`와 출처 허용목록이 그때 실제로 값을 한다.

## ADR-027 — 인증은 Google 위임, 세션은 Postgres 테이블, 관리자는 지정 계정
**상태:** Accepted (2026-08-20). `AGENTS.md`가 열어둔 "인증 방식 세부"를 닫는다.

**맥락:** 슬라이스 4에서 역할(`member|reviewer|admin`)과 권한 검사를 만들었지만
신원이 `X-User-Handle` 헤더였다. 헤더 하나로 검수자를 사칭할 수 있으니
권한 체계 전체가 모래 위에 있었다. 문서 세 곳이 이 때문에 프로덕션 배포를 금지하고 있었다.

**결정 셋:**

### 1. 로그인은 Google OAuth만

- **비밀번호를 다루지 않는다.** 해싱·재설정·유출 대응·크리덴셜 스터핑 방어가 전부 사라진다.
  1인 운영에서 이만한 절약이 없다.
- 다른 제공자를 넣지 않는다. 필요해지면 그때 추가한다.
- **ID 토큰(JWT)을 직접 검증하지 않는다.** 코드 교환이 서버 대 서버 TLS이므로,
  받은 액세스 토큰으로 userinfo를 한 번 부르면 된다.
  JWKS 캐싱과 서명 검증을 들이지 않는 만큼 틀릴 여지가 준다.
- **사용자 식별은 `google_sub`이다. 이메일이 아니다.** 이메일은 바뀌고,
  Google이 재사용하지 않는다고 보장하는 것은 `sub`뿐이다.

### 2. 세션은 Postgres 테이블

- **즉시 회수가 가능해야 한다.** 검수 권한이 있는 서비스에서 "이 계정 지금 끊어라"가
  안 되면 사고가 났을 때 할 수 있는 게 없다.
- **토큰을 평문으로 저장하지 않는다. sha256만 저장한다.**
  DB가 유출돼도 그 값으로 로그인할 수 없다. 비밀번호와 같은 이유다.
- 쿠키는 `HttpOnly` + `SameSite=Lax`. `Secure`와 `Domain`은 환경변수로 제어한다 —
  로컬 http에서는 `Secure`를 꺼야 붙는다. **프로덕션에서 켜는 것을 잊지 말 것.**
- 수명 30일, 갱신 없음.

**서명 쿠키(JWT)를 기각한 이유:** DB 조회가 없어 빠르지만 만료 전에 무효화할 수 없다.
권한을 빼거나 계정을 정지해도 토큰이 살아 있다. 무효화 목록을 두면 결국 테이블이 생기고,
그때는 "빠르다"는 장점도 사라진다.

### 3. 관리자는 지정된 Google 계정

`ADMIN_EMAIL`과 일치하는 계정으로 로그인하면 `admin`이 된다.

- **매 로그인마다 다시 판정한다.** 환경변수에서 빼면 다음 로그인에 권한이 사라진다.
- Google이 `email_verified: true`를 준 경우에만 대조한다.
- 비어 있으면 기동 실패. 관리자가 아무도 없는 배포는 사고다.
- 손으로 올려준 `reviewer`는 로그인해도 `member`로 내려가지 않는다.
  다만 `admin`은 `ADMIN_EMAIL`이 유일한 출처다.

**별도 비밀번호 관리자 계정을 두지 않은 이유:** Google 장애 시 비상구가 생기지만,
로그인 경로가 둘이 되고 비밀번호 해싱·변경 흐름이 되살아난다.
이 프로젝트 규모에서 비상구의 값어치보다 표면적이 크다.
정말 막히면 SQL로 `role`을 바꾸면 된다 — DB 접근은 어차피 필요하다.

**임시 장치 제거 — 우회로를 남기지 않는다:**

- `X-User-Handle` 삭제 (슬라이스 4의 임시 신원)
- `X-Admin-Token`과 `ADMIN_TOKEN` 삭제 (ADR-026 시점의 임시 운영 가드).
  관리자 엔드포인트는 이제 세션 + `role='admin'`이다.
- ADR-026의 CORS `AllowedHeaders`에서도 뺐다. 남은 것은 `Content-Type`뿐이다.

**둘 중 하나라도 남기면 인증을 붙인 의미가 없다.** 실제로 구 헤더로 호출해 401을 확인했다.

**결과:**

- 런타임 직접 의존성이 여덟이 된다 (`golang.org/x/oauth2` 추가).
- **OAuth 리다이렉트 엔드포인트(`/auth/google/*`)는 `openapi.yaml`에 넣지 않는다.**
  JSON을 주고받지 않고 브라우저가 직접 이동하는 302라, 계약에 넣어도 생성기가
  쓸모없는 클라이언트를 만들 뿐이다. 라우터에 직접 단다.
  `/auth/me`와 `/auth/logout`은 JSON이라 계약에 있다.
- 로그인 성공 후 돌아갈 웹 주소(`LOGIN_SUCCESS_REDIRECT`)와 로그인 시작 주소
  (`VITE_LOGIN_URL`)를 환경변수로 둔다. 웹과 API가 다른 출처라 하드코딩할 수 없다.
- **읽기 화면은 비로그인도 볼 수 있다.** 로그인이 필요한 것은 제안·검수·관리뿐이다.
  세션 미들웨어는 사용자를 컨텍스트에 싣기만 하고, 거부는 오퍼레이션별로 한다.

## ADR-028 — Cloudflare(D1 + Workers) 이전을 검토하고 현행 스택을 유지한다
**상태:** Accepted (2026-08-20). ADR-001·002·003을 재확인한다 — 뒤집지 않는다.

**맥락:** 운영 편의성 때문에 스택 전환을 검토했다. Cloudflare 대시보드가 손에 익어
인프라를 한곳에서 보고 싶다는 동기였고, R2를 이미 쓰고 있으니(ADR-008) 자연스러운 생각이다.
D1을 DB로, Workers를 런타임으로 쓰면 백엔드가 Node/TS가 되고 프론트와 언어가 통일된다.

**검토 결과 — D1로 가면 불변식 둘이 깨진다.**

1. **트랜잭션 안 잡 등록이 불가능하다.** ADR-003이 Redis 대신 River를 고른 **유일한 근거**이고,
   `TestRequestRollsBackBookWhenEnqueueFails`가 지키고 있다.
   Cloudflare Queues는 D1 트랜잭션에 참여하지 않으므로
   "책은 생성됐는데 잡 등록이 실패"하는 틈이 그대로 돌아온다.
2. **D1에 대화형 트랜잭션이 없다.** 원자적 `batch()`만 있고 중간에 읽어서 분기할 수 없다.
   승인 트랜잭션(불변식 3)은 읽고 → 판단하고 → 세 번 쓰는 구조라 그대로 옮겨지지 않는다.
   `pg_advisory_xact_lock`도 없어 **ADR-024를 다른 방식으로 다시 풀어야 한다** —
   40라운드 반복에서야 드러난 버그였다.

그 밖에 걸리는 것: 셰익스피어 7MB를 Worker 128MB에서 파싱해야 하는데
전략 체인이 트리 순회(`Find`/`Closest`/clone-remove)라 스트리밍 `HTMLRewriter`로는 안 되고,
`COPY` 39,355행이 배치 문장 제한에 걸려 여러 왕복으로 쪼개진다.

**결정:** 현행을 유지한다. Go + Railway + Postgres + River.

**남겨 두는 선택지 — 안 C.** 운영 편의성이 실제로 아프면 **D1 없이** Cloudflare로 갈 수 있다:
Workers + Hyperdrive + 관리형 Postgres(Neon 등) + `graphile-worker`/`pg-boss`.
두 큐 모두 트랜잭션 안 enqueue를 지원하므로 ADR-003이 살고 자문 잠금도 그대로 쓴다.
스키마는 거의 손대지 않고 애플리케이션 ~5,300줄만 옮기면 된다.
파서는 `cheerio`가 goquery와 API 계보가 같아 가장 순하게 옮겨지는 축이다.

**결과:**

- **이 검토를 다시 하지 않는다.** 다시 열 이유는 "운영이 실제로 아파서"여야지
  "Cloudflare를 써보고 싶어서"가 아니다.
- **배포 슬라이스를 먼저 해보고 판단하는 것이 옳다.** 지금 운영 부담은 추정이고,
  Railway 4서비스가 실물로 돌아본 적이 없다. 아프다는 것이 확인되면 안 C를 꺼낸다.
- 전환하기로 하면 **D1이 아니라 안 C**다. 위 둘을 다시 푸는 비용이 이전 이득보다 크다.

## ADR-029 — 빌드는 Nixpacks가 아니라 서비스별 Dockerfile로 한다
**상태:** Accepted (2026-08-20)

**맥락:** Railway는 Nixpacks 자동 감지로도 배포된다. 설정 파일이 없어도 되니 편하다.
그럼에도 Dockerfile을 쓰기로 했다.

처음 제기된 근거는 "메모리 최적화"였는데 **그것은 틀렸다.**
이미지 크기와 런타임 RSS는 다른 축이다. Go 바이너리의 상주 메모리는
distroless든 Nixpacks든 같다. 실제로 이 서비스의 메모리를 정하는 것은 파서다:

| 도서 | 입력 | 최대 힙 |
|---|---|---|
| 100 셰익스피어 전집 | 7.3MB | **310MB** |
| 4300 율리시스 | 1.7MB | 58MB |
| 1342 오만과 편견 | 0.9MB | 29MB |

전략 넷을 모두 돌리고 각각 DOM을 순회하므로 입력의 40배가 넘는 힙을 쓴다.
베이스 이미지를 아무리 줄여도 이 숫자는 안 변한다.

**결정:** Dockerfile을 쓴다. 근거는 셋이고, 메모리는 그중에 없다.

1. **결정성.** 이 저장소는 생성기 버전을 `go.mod` tool 디렉티브로 박고(ADR-020),
   pnpm을 `packageManager` 필드로 고정하고(ADR-019), 골든 스냅샷으로 회귀를 잡는다.
   Nixpacks 자동 감지는 블랙박스라 배포 시점에 따라 달라질 수 있다.
   **재현 가능성을 이만큼 챙긴 저장소에서 빌드만 추론에 맡길 이유가 없다.**
2. **어느 바이너리를 띄우는지 코드에 남는다.** `cmd/`에 넷이 있어
   Nixpacks에도 어차피 알려줘야 한다. 그럴 바에 Dockerfile이 낫다.
3. **이미지 크기와 공격 표면.** Go는 multi-stage + distroless static으로 20~30MB다.
   `web`은 런타임 이미지에서 devDependencies를 뺀다.

**구성:** Go 둘은 코드가 거의 같아 **Dockerfile 하나**로 낸다. `web`은 별도다.

> **개정 (ADR-031, 2026-08-20):** 원문은 여기서 `--build-arg CMD=api|worker`로 갈랐다.
> **Railway의 설정 표면에 빌드 인자가 없다.** 그 방법은 못 쓴다.
> 이미지 하나에 `api`·`worker`·`migrate`를 함께 빌드해 넣고 서비스별 `startCommand`로 가른다.
> Dockerfile을 쓴다는 결정 자체는 그대로다.

**주의점 둘:**

- **Go 런타임 이미지에 마이그레이션 SQL을 싣지 않는다.** 이미 `embed`로 바이너리 안에 있다
  (`internal/db/migrate.go`). distroless static을 쓰므로 `CGO_ENABLED=0`이어야 한다.
- **`web` 빌드 컨텍스트는 저장소 루트다.** `orval.config.ts`가 `../openapi.yaml`을
  참조하므로 `web/`만 컨텍스트로 잡으면 생성이 깨진다.

**결과:**

- 메모리 산정은 Dockerfile과 무관하게 실측으로 한다 —
  `worker` 1GB / `api`·`web` 512MB. `PARSE_CONCURRENCY`를 올리면 배수로 는다.
- Nixpacks로 돌아갈 이유가 생긴다면 그것은 "Dockerfile 유지가 부담"일 때다.
  지금 규모(서비스 셋, Dockerfile 둘)에서는 부담이 아니다.
- `.dockerignore`로 `.cache/`를 반드시 제외한다. Gutenberg 원본 수십 MB가 빌드 컨텍스트에 들어간다.

## ADR-030 — 마이그레이션은 Railway pre-deploy 명령으로 실행한다
**상태:** Accepted (2026-08-20). ADR-022가 정한 순서(goose → River)는 그대로다.

**맥락:** `make migrate`는 `tools/migrate`를 `go run`으로 돌린다. 로컬에서는 손으로 친다.
Railway에는 그 자리가 없다 — 서비스를 띄우는 것만 하지
"이 명령을 한 번 실행" 하는 자리가 기본적으로 없다.

순서가 틀리면 바로 깨진다. `00003_auth.sql`이 `sessions`를 만드는데,
그 SQL 없이 새 API 코드가 뜨면 로그인마다 `relation "sessions" does not exist`다.
**스키마가 코드보다 먼저 가 있어야 한다.**

**결정:** Railway pre-deploy 명령에서 `tools/migrate`를 실행한다.
새 버전을 띄우기 **전에**, 배포당 **한 번만** 돈다.

**대안과 기각 사유:**

- **일회성 서비스를 두고 손으로 실행** — 통제는 확실하지만 사람이 잊는다.
  마이그레이션이 포함된 배포에서 한 번 잊으면 그대로 장애다.
  잊지 않는 것에 기대는 절차는 언젠가 잊힌다.
- **`api` 기동 시 자동 실행** — 설정이 필요 없지만 **인스턴스가 여럿이면 경합한다.**
  Railway는 배포 교체 중 구/신 버전이 잠깐 함께 뜬다.
  **ADR-022가 이미 같은 이유로 기각한 방식**이고, 그 기각 근거가 Railway에서 실제로 성립한다.

**"실패하면 배포가 막힌다"는 단점이 아니다.** 스키마가 맞지 않는 코드가 뜨는 것보다
안 뜨는 것이 낫다. 막히는 것이 원하는 동작이다.

**결과:**

- **Go Dockerfile이 `tools/migrate`도 이미지에 넣는다.** 그래야 pre-deploy가 부를 수 있다.
  런타임 이미지가 바이너리 두 개를 담게 되지만 distroless static이라 수 MB 차이다.
- **pre-deploy는 `api` 서비스에만 건다.** `worker`에도 걸면 배포마다 두 번 돈다 —
  goose가 멱등이라 사고는 안 나지만 의미 없는 실행이고, 어느 쪽이 먼저인지 헷갈린다.
- 로컬은 `make migrate` 그대로다. 진입점이 둘로 갈리지만 같은 바이너리를 부른다.
- River 마이그레이션도 같은 진입점에서 이어 돈다 (ADR-022). 순서가 코드에 있다.

## ADR-031 — Railway 설정은 서비스별 `railway.json`에 둔다. 이미지는 하나로 합친다
**상태:** Accepted (2026-08-20). ADR-029의 "구성" 절을 개정한다. ADR-030은 그대로다.

**맥락:** Railway CLI(5.41.3)를 깔고 실제 설정 표면을 확인했다. 두 가지가 드러났다.

**1. 설정을 코드로 두는 방법이 둘인데, 하나는 이 슬라이스에 필요한 것을 못 담는다.**

| 모델 | 범위 |
|---|---|
| `.railway/railway.ts` (TypeScript IaC) | 프로젝트 전체 — 서비스·DB·버킷·볼륨·환경변수·replicas·도메인 |
| `railway.json` | 서비스 하나의 build·deploy 설정 |

이 슬라이스에 필요한 것은 셋이다 — 서비스별 **`dockerfilePath`**,
`api`에만 거는 **`preDeployCommand`**(ADR-030), 실측으로 정한 **메모리 상한**(ADR-029).
**셋 다 `railway.ts` DSL에 없다.** `railway.json` 스키마에는 셋 다 있다
(`build.dockerfilePath` · `deploy.preDeployCommand` · `deploy.limitOverride.containers.memoryBytes`).

그리고 **두 모델은 같은 서비스를 함께 관리할 수 없다.** 하나를 골라야 한다.

**2. Railway에는 Docker 빌드 인자를 넣을 자리가 없다.**
`railway.schema.json`의 `build` 섹션은 `builder`·`buildCommand`·`dockerfilePath`·
`watchPatterns`·`nixpacks*`·`railpackVersion`이 전부다. `args`가 없다.
**ADR-029가 정한 `--build-arg CMD=api|worker`는 Railway에서 성립하지 않는다.**

**결정 둘:**

1. **설정 모델은 `railway.json`.** 서비스마다 파일을 따로 둔다 —
   `railway.api.json` · `railway.worker.json` · `railway.web.json`.
2. **Go 이미지 하나에 `api`·`worker`·`migrate` 셋을 빌드해 넣고,
   서비스별 `deploy.startCommand`로 가른다.** 빌드 인자를 쓰지 않는다.

**대안과 기각 사유:**

- **`.railway/railway.ts`** — 프로젝트 전체를 한 파일로 기술하고 `plan`/`apply`로
  드리프트까지 잡는다. 이쪽이 상위 도구다. 그런데 **이 슬라이스가 필요한 설정 셋을 못 담는다.**
  담을 수 있게 되면 그때 옮긴다. 그전에 쓰면 나머지를 대시보드에 흩어 두게 된다.
- **설정 파일 없이 CLI로만** (`railway environment edit --service-config <svc> <경로> <값>`) —
  동작은 확인된 방법이고 실제로 `build.dockerfilePath`·`deploy.startCommand`·
  `source.rootDirectory`를 점 경로로 넣을 수 있다. 그런데 **그러면 설정이 저장소 밖에만 있다.**
  이 저장소는 생성기 버전을 `go.mod` tool로 박고(ADR-020) pnpm을 `packageManager`로
  고정한다(ADR-019). 재현 가능성을 이만큼 챙겨 놓고 빌드·배포 설정만 대시보드에 두는 것은 앞뒤가 안 맞는다.
- **서비스마다 Dockerfile을 따로** — 빌드 인자 없이도 가를 수 있지만 Go 빌드 단계가 복제된다.
  **ADR-030이 이미 한 이미지에 바이너리 둘을 넣기로 했다.** 셋으로 느는 것은 그 연장이지 새 방향이 아니다.

**결과:**

- **런타임 이미지에 바이너리 셋.** distroless static이라 10MB 안팎 차이다.
  `api`는 `/api`, `worker`는 `/worker`, pre-deploy는 `/migrate`를 부른다.
- **`preDeployCommand`는 문자열 하나 또는 원소 하나짜리 배열이다** (스키마 `maxItems: 1`).
  명령을 여럿 엮을 수 없다. `tools/migrate`가 goose와 River를 이어 도는 이유가 여기서도 산다 (ADR-022).
- **시크릿을 `railway.json`에 넣지 않는다.** 이 파일은 커밋된다. 값은 Railway 변수로 간다.
- **미확인 둘.** 정직하게 남긴다.
  - **서비스별 설정 파일 경로 지정.** Railway 서비스 설정 항목이다.
    CLI 점 경로 목록에 없다 — 대시보드에서 서비스당 한 번 지정해야 할 수 있다.

    **문서 확인 (2026-08-20):** 공식 문서 `config-as-code`에 항목이 있다 —
    *"You can use a custom config file by setting it on the service settings page.
    You should provide the absolute path to the file in your repository"*.
    **대시보드 서비스 설정에서 저장소 절대 경로**(`/railway.api.json`)를 넣는 것이 맞다.
    CLI로 되는지는 여전히 미확인. **실물 확인은 배포할 때 한다.**
  - **`deploy.limitOverride`.** JSON 스키마에는 있는데 Railway 공개 문서에는 없고
    CLI 점 경로 목록에도 없다. 안 먹으면 메모리는 대시보드로 간다.

    **스키마 재확인 (2026-08-20):** `deploy.limitOverride.containers.memoryBytes`가
    스키마에 실재한다(`cpu`·`memoryBytes`·`diskBytes`). 다만 `config-as-code/reference`의
    "Configurable settings" 목록에는 **여전히 없다.** 파일에 적어 두되 **먹는지는 배포 후 확인한다.**

  둘 다 서비스당 한 번뿐이라 막히지 않는다. 배포할 때 확인하고 이 ADR에 결과를 적는다.

- **덤으로 확인된 것 둘** (문서, 2026-08-20). 둘 다 이 구성의 전제였다.
  - **`startCommand`는 exec form으로 이미지의 `ENTRYPOINT`를 덮는다.**
    셸을 거치지 않는다 — **distroless에 셸이 없어도 `/api`가 뜬다.**
    대신 **변수 확장이 안 된다.** `startCommand`에 `$PORT`를 쓰지 말 것.
    Go 코드가 `PORT`를 직접 읽는 지금 구조가 맞다.
  - **pre-deploy는 애플리케이션 이미지로, 프라이빗 네트워크 안에서, 서비스 환경변수를 갖고 돈다.**
    실패하면 재시도 없이 배포가 멈춘다 — ADR-030이 원한 동작 그대로다.
    **별도 컨테이너라 파일시스템 변경은 남지 않는다.** `tools/migrate`는 DB만 건드리므로 무관하다.

## ADR-032 — 클라이언트 번들에 박히는 값은 빌드 인자로 받는다
**상태:** Accepted (2026-08-20). ADR-031의 "빌드 인자" 서술을 정정한다. 결정은 그대로다.

**맥락:** ADR-031은 `railway.schema.json`의 `build` 섹션에 `args`가 없는 것을 보고
**"Railway에는 Docker 빌드 인자를 넣을 자리가 없다"**고 적었다. **그 서술이 부정확하다.**

없는 것은 **임의의 빌드 인자를 설정 파일에 선언하는 자리**다.
서비스 변수는 빌드에 들어간다 — 다만 **Dockerfile에 같은 이름의 `ARG`를 선언해야만** 한다.
Railway 문서(`builds/dockerfiles` — "Using variables at build time")가 명시한다:

> you must specify them in the Dockerfile using the `ARG` command […]
> Be sure to declare your environment variables in the stage they are required in

**이게 왜 문제가 되는가.** Vite는 `import.meta.env.VITE_*`를 **빌드 시점에 상수로 치환**한다.
런타임 환경변수가 아니다. 이 저장소에서 그런 값이 둘이다:

| 값 | 쓰이는 곳 |
|---|---|
| `VITE_API_URL` | `web/src/api/http.ts` — 브라우저가 부를 API 주소 |
| `VITE_LOGIN_URL` | `web/src/routes/__root.tsx` — 로그인 시작 주소 |

`ARG`를 선언하지 않으면 Railway 변수에 값을 넣어도 빌드에 들어오지 않는다.
번들에는 `undefined`가 박히고, **배포는 성공한 것처럼 보이는데 브라우저에서만 죽는다.**
SSR은 `API_INTERNAL_HOST`를 런타임에 읽으므로 첫 화면은 뜬다 — 그래서 더 늦게 발견된다.

**결정:**

1. **`web/Dockerfile`이 빌드 스테이지에서 `ARG VITE_API_URL` · `ARG VITE_LOGIN_URL`을 선언한다.**
2. **비어 있으면 빌드를 세운다.** `pnpm build` 앞에서 `test -n`으로 막는다.
   기본값을 조용히 채우지 않는다는 규약(CONVENTIONS)을 빌드 시점으로 옮긴 것이다.
   깨진 번들을 배포하는 것보다 빌드가 실패하는 것이 낫다 — ADR-030의 판단과 같은 형태다.

**결과:**

- **웹 이미지는 도메인에 묶인다.** 도메인이나 API 주소가 바뀌면 변수만 고치고 재시작하는 것으로
  안 된다. **재빌드해야 한다.** Go 이미지는 영향이 없다 — 설정을 전부 런타임에 읽는다.
- **`VITE_*`는 웹 서비스를 처음 배포하기 전에 넣어야 한다.** 순서가 §6.1(도메인)에 걸린다.
- **ADR-031의 결정은 그대로다.** 서비스 변수로 `CMD=api|worker`를 넘겨 이미지를 가르는 것도
  이론상 가능하지만, 그러면 **서비스마다 이미지를 따로 빌드**하게 된다.
  한 이미지 + `startCommand`가 여전히 낫다.
- Go 쪽은 `RAILWAY_GIT_COMMIT_SHA`만 `ARG`로 받는다. `/healthz`의 `version`에 배포된 커밋이 뜬다 —
  어느 빌드가 살아 있는지 확인하는 데 쓴다.

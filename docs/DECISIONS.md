# 설계 결정 이력 (ADR)

새 결정은 맨 아래에 추가한다. 기존 항목은 지우지 않는다.
결정을 뒤집을 때는 해당 항목의 상태를 `Superseded by ADR-NNN`으로 바꾸고 새 항목을 추가한다.

상태: `Accepted` / `Proposed` / `Superseded` / `Rejected`

## ADR-001 — 백엔드는 Go, MSA로 쪼개지 않는다
**상태:** Accepted

**맥락:** MSA 구성을 검토했다. 도메인이 수집·번역 둘뿐이고 1인 개발 규모다.

**결정:** Go 모듈 하나에 `cmd/api`, `cmd/worker` 두 바이너리. 서비스를 더 쪼개지 않는다.
확장이 필요하면 같은 바이너리를 다른 큐만 소비하도록 추가 기동한다.

**결과:** 배포 단위가 적어 Railway 운영이 단순하다. 도메인 경계가 검증된 뒤에야 분리를 재검토한다.

---

## ADR-002 — 배포는 Railway
**상태:** Accepted

**맥락:** 초기 규모에 맞는 관리형 플랫폼이 필요했다.

**결정:** Railway. api / worker / postgres / web 네 서비스.

**결과:** k8s 프리미티브(서비스 메시, 카나리)는 쓸 수 없다. 관측성은 외부 도구(OTel)를 붙여야 한다.
프라이빗 네트워크가 IPv6 전용이라 `[::]` 바인딩이 강제된다.

---

## ADR-003 — 잡 큐는 River (Redis 아님)
**상태:** Accepted

**맥락:** asynq(Redis)와 River(Postgres)를 비교했다.

**결정:** River. Postgres 트랜잭션 안에서 enqueue가 가능한 것이 결정적이었다.
"책 레코드는 생성됐는데 잡 등록이 실패"하는 틈이 생기지 않는다.

**결과:** Railway 서비스가 하나 줄어든다(Redis 불필요). 처리량 한계는 Postgres에 종속된다.

## ADR-004 — 번역은 `paragraph_stable_id`에 결합한다
**상태:** Accepted

**맥락:** 파서를 개선해 재파싱하면 문단 행 ID가 밀린다. 번역이 `paragraphs.id`를 참조하면
모든 번역이 엉뚱한 문단에 붙는다.

**결정:** `stable_id = sha256(정규화된 본문)[:16]`. 번역 테이블은 FK 대신 이 값을 참조한다.
파싱 결과는 불변 `book_revisions`로 쌓는다.

**결과:** FK 무결성을 포기하는 대신 재파싱이 안전해진다. revision 전환 시 해시 매칭으로 승계한다.
이 프로젝트에서 가장 되돌리기 어려운 지점이므로 우선순위가 높다.

**보완:** 같은 본문이 한 책에 반복되면 이 정의만으로는 번역 행이 공유된다.
2번째 등장부터 등장 순서를 붙이는 규칙을 **ADR-016**에서 더했다. 이 항목을 뒤집지는 않는다 —
첫 등장의 `stable_id`는 위 정의 그대로다. 전체 규칙은 `docs/ARCHITECTURE.md` 핵심 불변식 1 참조.

## ADR-005 — 문단당 확정 번역 1개를 스키마로 강제한다
**상태:** Accepted

**맥락:** 여러 사용자가 제안하고 검수를 거쳐 하나만 공개하는 모델이다.

**결정:** `translation_proposals`(N개)와 `paragraph_translations`(0 또는 1개)를 분리하고,
후자에 복합 PK `(project_id, paragraph_stable_id)`를 건다.
승인은 한 트랜잭션 안에서 처리하며 `WHERE status = 'pending'` 조건으로 동시 승인을 막는다.

**결과:** 불변식이 애플리케이션이 아니라 DB에서 지켜진다.

## ADR-006 — 웹은 TanStack Start (SSR)
**상태:** Accepted

**맥락:** 검색 노출이 필요하다. Go 템플릿 + 별도 SPA, Next.js, TanStack Start를 비교했다.

**결정:** TanStack Start. 2026-03 v1.0 릴리스로 안정화됐다.
읽기 화면은 SSR, 편집·검수 화면은 CSR로 **같은 라우터 안에서** 라우트별로 나눈다.

**결과:** 프론트를 두 벌 만들지 않아도 된다. 대신 Node 서비스가 하나 늘고,
API 베이스 URL을 서버·클라이언트에서 분기해야 한다.
비즈니스 로직이 server function으로 새지 않도록 규칙을 둔다(AGENTS.md 참조).

## ADR-007 — 원문 페이지는 색인하지 않는다
**상태:** Accepted

**맥락:** Gutenberg 원문은 이미 수백 개 사이트에 존재한다. 신생 도메인이 중복 경쟁에서 이길 수 없다.

**결정:** 원문 전용 페이지는 `noindex, follow`. 번역 페이지가 canonical이자 색인 대상.
승인 커버리지가 임계값 미만인 챕터도 `noindex`.

**결과:** 크롤 예산이 고유 콘텐츠(번역문)에 집중된다. 임계값 수치는 미정(ADR 추가 필요).

## ADR-008 — 스토리지는 Cloudflare R2
**상태:** Accepted

**맥락:** Railway에는 오브젝트 스토리지가 없다. 원본 HTML 스냅샷을 보관해야 하고,
재파싱 때마다 다시 읽는다.

**결정:** Cloudflare R2. S3 호환이라 `aws-sdk-go-v2`를 그대로 쓴다.

**결과:** egress가 무료라 재파싱 비용 부담이 없다.

## ADR-009 — API는 스펙 우선 (OpenAPI)
**상태:** Accepted

**맥락:** Go 백엔드와 TS 프론트의 타입을 일치시켜야 한다.

**결정:** `openapi.yaml`이 단일 원본. `oapi-codegen`으로 Go 인터페이스를,
`orval`로 TS 클라이언트와 react-query 훅을 생성한다.

**결과:** 계약 변경이 양쪽에서 컴파일 에러로 드러난다. 생성 코드는 손으로 고치지 않는다.

## ADR-010 — LLM 번역 제안은 초기 범위에서 제외한다
**상태:** Accepted

**맥락:** 문단별 LLM 번역 제안을 검토했으나 초기 기획에서 뺐다.
개인 사용자는 LLM 요청 권한이 없다.

**결정:** 제안 생성은 전부 사람 손. `llm_suggestions` 테이블과 SSE 스트리밍,
레이트리밋, Anthropic SDK 의존성 모두 넣지 않는다.

**결과:** API가 평범한 JSON 엔드포인트만으로 구성된다.
`book_glossary`는 남긴다 — 여러 사용자가 같은 책을 번역할 때 인명·호칭 일관성 문제가
사람 번역에서도 동일하게 발생하며, 나중에 LLM을 붙일 때 프롬프트 프리픽스로 재사용된다.

---

## ADR-011 — 파서 검증을 스켈레톤보다 먼저 한다
**상태:** Accepted

**맥락:** Gutenberg HTML의 자동 분리 성공률이 설계를 바꾼다.
성공률이 높으면 수동 검토는 예외 처리 수준이면 되고, 낮으면 관리자 보정 UI가 핵심 기능이 되며
스키마에 보정 레이어가 필요해진다.

**결정:** `cmd/parsecheck` 스파이크로 실제 도서 15~20권을 추출해 리포트를 먼저 낸다.
그 결과를 보고 스켈레톤을 만든다.

**결과:** 스파이크의 `extractor.go`는 버리지 않고 `internal/parse/`로 이관한다.
원본 HTML은 커밋하지 않고 `corpus.json`(도서 ID)과 `golden/`(추출 결과 요약)만 남긴다.

## ADR-012 — 정규화에 `golang.org/x/text`를 쓴다
**상태:** Accepted

**맥락:** `stable_id` 정규화는 Unicode NFC가 필수다 (SPIKE_PARSER §5.7, 불변식 1).
스파이크 의존성 화이트리스트는 `goquery`와 `golang.org/x/net/html`뿐이었다.

**결정:** `golang.org/x/text/unicode/norm`을 추가한다. NFC를 손구현하지 않는다.

**결과:** `x/text`는 Go 확장 라이브러리다. 정규화 규칙은 그대로고, 의존성만 명세보다 하나 늘었다.

## ADR-013 — 파서 후처리: 앞부분 문단 보존, 빈 챕터, 제목 정리, 이미지 이니셜
**상태:** Accepted (2026-08-19)

**맥락:** 스파이크 공식 신뢰도는 22/22 자동이다. 그러나 `anchor-toc`는 목차 항목을 빈 챕터로 한 번 더 만들고,
첫 챕터 경계보다 앞에 있는 문단을 조용히 버리며, 삽화본 `h2`는 캡션을 장 제목에 붙이고,
이미지 드롭캡은 문단 첫 글자를 지운다. 상세는 `docs/PARSER_REPORT.md`.

> **검증 이력.** 이 초안은 두 번 정정됐다. 둘 다 리포트 수치를 코드 동작과 대조하다 드러났다.
> 1. **드롭캡 범위** — 초안은 5권(1342·345·98·1400·1661)을 대상으로 잡았다. 그것은
>    `dropcap`/`letra` **클래스가 등장한 문단 수**였고 평문 대조값이 아니었다. 텍스트 노드 드롭캡은
>    이미 정상 추출된다. 실제 유실은 이미지 이니셜뿐이고 1342 한 권 56문단이다.
>    초안대로 구현했다면 멀쩡한 4권에서 첫 글자가 중복됐다.
> 2. **문단 유실 원인** — 2차 초안은 "경계로 쓴 `<p>`의 본문을 버린다"로 적었다.
>    순회 로직을 재현해 분류한 결과 **유실 66건 중 65건은 첫 챕터 경계보다 앞에 있어서**
>    버려진 것이었다(`strategy_anchor_toc.go`의 `cur < 0` 분기). 경계로 쓰여 버려진 것은 1건뿐이다.
>    2차 초안대로 구현했다면 셰익스피어 1건만 고쳐졌다.

**결정:** 전략 점수 계산 뒤에 후처리를 둔다. 심각도 순이다.

1. **첫 챕터 경계 이전의 문단을 front-matter 챕터(idx 0)로 보존하고 `warnings`에 남긴다.**

   지금은 `cur < 0`이라 그냥 버려진다. 사라지는 양은 커버리지 1% 미만이라 신뢰도 공식에 잡히지 않고,
   관리자도 사라진 줄을 알아볼 수 없다.

   | 권 | 유실 `<p>` | 경계 이전 | 경계로 쓰임 | 사라진 내용 |
   |---|---|---|---|---|
   | 76 Huckleberry Finn | 51 | 51 | 0 | 목차형 `<p>` 다수 + 방언 설명 노트 |
   | 74 Tom Sawyer | 5 | 5 | 0 | **저자 서문 전체** |
   | 46 Christmas Carol | 4 | 4 | 0 | **저자 서문 전체** |
   | 345 Dracula | 4 | 4 | 0 | 표제지 |
   | 1524 Hamlet | 1 | 1 | 0 | 등장인물 목록 |
   | 205 Walden | 1 | 1 | 0 | 서두 인용 |
   | 100 Shakespeare | 1 | 0 | 1 | THE PROLOGUE 전문 |

   **전부 살리는 것도 답이 아니다.** 앞부분에는 살려야 할 것(74·46 서문, 1524 등장인물, 205 에피그래프)과
   버려야 할 것(76의 목차형 `<p>`, 345 표제지)이 섞여 있다.
   **판별을 파서가 떠맡지 않는다.** 일단 보존하고 경고를 남기면 관리자가 보고 즉시 판단할 수 있다.
   조용히 사라지는 지금이 최악이다. 76의 목차형 `<p>`는 별건으로 `ExcludeSelector` 보강을 검토한다.

   `section-chapter`도 같은 증상이 있다 — 첫 `section.chapter` 바깥의 문단이 수집되지 않는다
   (2542 인형의 집 등장인물 목록 187자). 후처리는 전략에 무관하게 적용한다.

   부수 효과: 앞부분 문단이 있는 권은 챕터가 하나씩 늘어난다.

2. **문단 0개 챕터 제거.**

   검증 완료. 정리 후 챕터 수가 실제 목차와 일치한다.

   | 권 | 현재 | 빈 챕터 | 정리 후 | 실제 |
   |---|---|---|---|---|
   | 84 Frankenstein | 56 | 28 | 28 | 편지 4 + 24장 |
   | 345 Dracula | 54 | 27 | 27 | 27장 |
   | 1524 Hamlet | 40 | 20 | 20 | 20 scene |
   | 46 Christmas Carol | 10 | 5 | 5 | Stave 5 |

   **1번과 충돌하지 않는다.** 빈 챕터를 만든 경계 요소는 전수 확인 결과 전부 `<a>` 앵커였다
   (84·345·46·74·1524·205). 1번이 `<p>`를 살려도 이 챕터들은 여전히 비어 있어 정상 제거된다.

   단, 1080(겸손한 제안)은 이 규칙만 적용하면 남는 챕터 제목이 `1729`가 된다.
   짧은 산문의 표제지 처리는 별건이며 이 ADR의 범위가 아니다.

3. **헤딩 정리 — 삽화 캡션과 페이지 번호.**

   1342의 `h2`는 캡션과 장 제목이 한 태그에 있어 `I hope Mr. Bingley will like it. CHAPTER II.`가 된다.
   `.caption` 제거로 해결된다.

   여기에 더해 **제목 전체가 페이지 번호인 경우**를 따로 다룬다. 1342의 챕터 `{ix}`(16문단),
   `{xxv}`(1문단)가 그렇다. 캡션 오염이 아니라 제목 자리에 페이지 마커만 있는 경우이고,
   내용은 실제 서문이라 챕터째 버릴 수도 없다. 제목만 비우거나 front-matter로 넘긴다.

4. **이미지 이니셜 복원 — `img alt`가 한 글자일 때만.**

   텍스트 노드 드롭캡(`.dropcap`/`.letra`)은 건드리지 않는다. 대상은 1342의 56문단이다.
   `alt`가 비었거나 여러 글자면 복원하지 않고 `warnings`에 남긴다.

5. **후처리 후 신뢰도를 재계산한다.**

   전략 **선택**은 후처리 전 원본 점수로 한다(전략별 성능 비교가 왜곡되지 않도록).
   그러나 저장되는 `confidence`와 golden 스냅샷은 **후처리 후 결과로 다시 계산한다.**
   그러지 않으면 0.85 자동 확정 게이트가 실제 저장물이 아닌 것을 근거로 판단한다.

   리포트 권고 4의 `emptyChapterRatio` 페널티는 이 항목에 종속된다 —
   후처리로 빈 챕터가 사라지면 그 페널티는 의미가 없어지므로, 재계산 도입 후 필요성을 다시 본다.

**결과:**

- 스키마 보정 레이어는 이 후처리 이후에도 남는 책만 대상으로 다시 판단한다.
  리포트 권고 2("지금은 넣지 말 것")가 그대로 유지된다.
- `stable_id` 등장 순서 부여(ADR-016)도 이 후처리 단계에서 함께 한다. 두 작업은 같이 구현한다.
- **golden 스냅샷 22권이 전부 바뀐다.** 챕터 수(§1·§2)와 문단 수(§1)가 달라지고,
  §5의 재계산으로 `confidence`까지 변한다. 갱신은 `make golden GOLDEN_UPDATE=1`이지만,
  **갱신 전에 `make parsecheck` 리포트로 눈 검증을 반드시 거친다.**
  "왜 바뀌었는지 확인하고 갱신"이 지켜지지 않으면 golden이 회귀 검증 기능을 잃는다.
- 1080(짧은 산문의 표제지)과 76의 목차형 `<p>` 제외는 이 ADR의 범위 밖으로 남는다.

## ADR-014 — 합본은 단권으로 수집하지 않는다
**상태:** Accepted (2026-08-19)

**맥락:** Gutenberg 100(셰익스피어 전집)은 파싱·메모리 모두 된다. 결과는 챕터 1684개, 절반이 빈 목차 항목이고
후처리 후에도 842챕터 39,354문단이다. 읽기·번역 UI가 성립하지 않는다.

초안에는 판정 기준이 없었다. `mega`는 스파이크 `corpus.json`의 메타데이터일 뿐 프로덕션에 존재하지 않으므로,
관리자가 카탈로그에서 100번을 고르면 막을 것이 없다.

**결정:** 합본을 **크기로 판정한다.** 코퍼스상 임계값은 깨끗하게 잡힌다.

| | 챕터 | 문단 |
|---|---|---|
| 100 Shakespeare | **1,684** | **39,354** |
| 2701 Moby Dick (챕터 2위) | 145 | 2,487 |
| 4300 Ulysses (문단 2위) | 21 | 7,064 |

- 기준: **챕터 200 초과 또는 문단 15,000 초과.** 어디에 그어도 100만 걸리고 나머지 21권은 안전하다.
- 판정 시점은 **파싱 후**다. 수집 전에는 크기를 알 수 없다.
- 초과 시 **하드 차단이 아니라 관리자 확인 큐로 보낸다.** 차단하면 나중에 작품 단위 분할을 붙일 때
  되돌리기 번거롭다. 나중에 넣는다면 작품 단위로 나눈 뒤에만 받는다.

**결과:** 100번은 수집은 되되 자동 확정되지 않는다. 임계값은 코퍼스 22권 기준이므로,
더 큰 합본이 들어오면 재검토한다. `corpus.json`의 `mega` 분류는 스파이크 기록으로만 남기고
프로덕션 판정에는 쓰지 않는다.

## ADR-015 — 희곡은 초기 지원 범위에서 제외한다
**상태:** Accepted (2026-08-19)

**맥락:** 스파이크는 희곡의 정답을 "깨끗한 실패"로 가정했다. 그런데 최신 `pg-images.html`에서는
실패하지 않았다 — 인형의 집은 ACT I–III(491/434/385문단), 햄릿은 후처리 후 20 scene으로
깨끗하게 갈리고 대사는 `p`다. 즉 **파서가 못 해서 빼는 것이 아니다.**

남는 것은 제품 질문이었다. 번역 단위를 act/scene + 대사 문단으로 둘 것인가,
대사 문단에 화자명이 포함되는 것(`"LAERTES. What ceremony else?"`)을 어떻게 다룰 것인가.

**결정:** 희곡을 **초기 지원 범위에서 뺀다.** 추후 반영 후보로 남긴다.

**구현 방식 — 코드 게이트를 넣지 않는다.**

장르 자동 판별은 ADR-014의 크기 판정과 다르다. 챕터 200·문단 15,000처럼 코퍼스에서
깨끗하게 갈리는 임계값이 없다. `PARSER_REPORT.md` §6이 적었듯 장르 감지는
"화자 짧은 문단, ACT/SCENE" 같은 별도 휴리스틱이 필요하고, 잘못 만들면
**산문을 희곡으로 오판해 막는다.** 없는 게이트보다 틀린 게이트가 나쁘다.

따라서 제외는 **도서 선정 단계의 운영 정책**이다. 관리자가 희곡을 고르지 않는다.

**검증 코퍼스는 그대로 둔다.** `corpus.json`의 2542(인형의 집)·1524(햄릿)는
파서 검증 fixture이고 구조 다양성 확보가 목적이다. **지우지 말 것.**
이 결정은 프로덕션 도서 선정에 관한 것이지 테스트 데이터에 관한 것이 아니다.

**결과:**

- 파서 작업이 필요 없다. 나중에 넣기로 하면 **도서를 추가하기만 하면 된다.**
  진입 비용이 낮게 유지되므로 서두를 이유가 없다.
- 대사 중복 문제(햄릿 4.9%)는 ADR-016이 이미 해결했다. 나중에 희곡을 넣어도 이 축은 안전하다.
- 다시 검토할 때 남는 질문 두 개:
  번역 단위를 act/scene 챕터 + 대사 문단으로 둘 것인가,
  대사에 붙은 화자명을 번역 대상에 포함할 것인가.
- 운문은 이 코퍼스로 검증되지 않았다(1727은 Butler **산문** 번역이다).
  운문 지원은 별건이며 검증부터 다시 해야 한다.

## ADR-016 — 반복 본문의 `stable_id` 충돌은 등장 순서로 분리한다
**상태:** Accepted (2026-08-19). ADR-004를 보완한다 — 뒤집지 않는다.

**맥락:** ADR-004는 `stable_id = sha256(정규화 본문)[:16]`으로 정의했고,
`paragraph_translations`의 PK는 `(project_id, paragraph_stable_id)`다(ADR-005).
해시 입력이 본문뿐이므로 **본문이 같은 문단은 책의 서로 다른 위치에 있어도 번역 행 하나를 공유한다.**
제안(`translation_proposals`)도 같은 키를 쓰므로 제안·검수·읽기 화면이 모두 함께 묶인다.

스파이크 재검증에서 규모가 확인됐다. 파서의 더블카운팅이 아니라 원문에 실제로 반복되는 문장이다
(발생 위치가 전부 다른 챕터·인덱스).

| 권 | 총 문단 | 자리를 잃는 문단 | 비율 |
|---|---|---|---|
| 100 Shakespeare | 39,354 | 2,136 | 5.4% |
| 1524 Hamlet | 1,376 | 67 | 4.9% |
| 345 Dracula | 1,945 | 64 | 3.3% |
| 1661 Sherlock Holmes | 2,523 | 42 | 1.7% |
| 98 A Tale of Two Cities | 3,259 | 53 | 1.6% |
| 4300 Ulysses | 7,064 | 72 | 1.0% |

22권 중 6권은 중복이 0이다. 중복의 거의 전부가 60자 이하 짧은 대사다.

**결정:** 같은 본문의 **첫 등장은 지금과 동일하게** `sha256(text)`를 쓰고,
2번째 이후만 등장 순서를 붙인다.

```
n = 1  →  stable_id = sha256(normalized)[:16]              (현행과 완전히 동일)
n ≥ 2  →  stable_id = sha256(normalized + "#" + n)[:16]
```

순서 부여는 **파서 후처리 단계**에서 한다(ADR-013 후처리 뒤, 챕터·문단 순서가 확정된 시점).
`Normalize`에는 넣지 않는다 — 앞선 문단을 알아야 하므로 순수 함수가 깨지기 때문이다
(SPIKE_PARSER §5.7의 "정규화 함수는 순수 함수여야 한다"를 유지).

### 왜 안 C인가 — 검토한 세 안

**안 A(현행 유지, 충돌 허용) — 기각.** 제품 결정이다.
영어 `"Yes."`는 화자와 상대에 따라 `"네."` / `"그래."` / `"예, 그렇습니다."`로 달라져야 하는데,
행이 하나뿐이면 **같은 원문이 나오는 모든 자리에 같은 존댓말이 강제된다.**
번역자가 화자별로 다르게 옮길 방법이 아예 없다.
용어 일관성은 `book_glossary`가 담당하므로(ADR-010), 대사까지 강제로 통일할 이유가 없다.

**안 B(위치를 해시에 포함, `sha256(chapter_idx + para_idx + text)`) — 기각.**
충돌은 사라지지만 **ADR-004의 존재 이유를 스스로 무효화한다.**
ADR-004는 "재파싱하면 문단 행 ID가 밀린다"를 풀려고 만들어졌는데,
안 B는 위치를 해시에 넣어 "밀리면 깨진다"를 되살린다. `paragraphs.id`를 참조하는 것과 실질적으로 같고,
FK 무결성만 포기하고 얻는 것이 없다.

이건 이론이 아니라 당장 닥친다. **ADR-013(빈 챕터 제거)을 적용했을 때 기존 id 생존율**을
코퍼스 22권으로 시뮬레이션한 결과:

| | 안 B 생존 | 안 C 생존 |
|---|---|---|
| **22권 평균** | **32.5%** | **100.0%** |
| 84 Frankenstein (빈 챕터 28) | 0.3% | 100% |
| 345 Dracula (27) | 0.1% | 100% |
| 100 Shakespeare (842) | 0.0% | 100% |
| 1524 Hamlet (20) | 0.0% | 100% |
| 76 Huckleberry Finn (44) | 0.0% | 100% |
| 1400 Great Expectations (0) | 100% | 100% |

15권에서 거의 전멸한다. 100% 생존한 7권은 빈 챕터가 0이라 아무것도 밀리지 않은 책들뿐이다 —
즉 안 B가 살아남는 조건은 "파서 결과가 하나도 안 바뀐 경우"다.
챕터 하나만 지워져도 뒤따르는 모든 챕터의 `chapter_idx`가 밀리고, 그 안 모든 문단의 id가 바뀐다.
지역적 변경이 전역적 id 변경으로 증폭된다.

부작용이 하나 더 있다. 안 B에서는 본문이 한 글자도 안 바뀌어도 위치만 밀리면 해시가 달라지므로,
ADR-004의 revision 전환 규칙에서 **"해시 일치 → 자동 승계"가 사실상 발동하지 않고**
전부 관리자 확인 큐로 쏟아진다. 위대한 유산이면 3,833건, 셰익스피어면 39,354건이다.
큐가 예외 처리용이 아니라 주 작업이 된다.

**안 C(반복분에만 등장 순서) — 채택.**
해시 입력이 본문뿐이라 위치가 아무리 밀려도 본문이 같으면 id가 같다. 위 시뮬레이션에서 100% 생존한다.
첫 등장의 id를 바꾸지 않으므로 **중복 없는 문단(대다수)과 중복 0인 6권은 영향이 전혀 없다.**
충돌 위험은 "같은 본문을 가진 문단들" 안으로 갇힌다.

**결과:**

- 문단당 확정본 1개(불변식 2)와 재파싱 안전성(불변식 1)을 둘 다 유지한다.
- `paragraph_translations` / `translation_proposals`의 스키마는 바뀌지 않는다.
  `stable_id`를 만드는 규칙만 바뀐다.
- **남는 위험:** 같은 본문의 반복 사이에 새 반복이 끼어들면 뒤쪽 순서가 밀린다.
  드라큘라 `"Jonathan Harker's Journal."` 9회 중 앞쪽에 하나가 새로 잡히면 뒤 8개가 +1 된다.
  영향이 그 텍스트에만 갇히고 건수도 작아서, ADR-004의 "유사 → 관리자 확인 큐"가 받아낸다.
- 본문 자체가 바뀌면(예: ADR-013의 이미지 이니셜 복원 56문단) 어떤 방식으로도 id가 바뀐다.
  이는 ADR-004가 설계상 받아내기로 한 부분이다.
- 구현: `internal/parse/postprocess.go`의 `assignOccurrenceIDs`. `Normalize`는 순수 함수로 그대로다.

## ADR-017 — 마이그레이션은 goose, DB 드라이버는 pgx/v5
**상태:** Accepted (2026-08-19)

**맥락:** `ARCHITECTURE.md`와 `AGENTS.md`는 `internal/db/migrations/`에 순번 SQL을 두고
`make migrate`로 적용한다고만 정했다. **러너는 미지정이었다.**
sqlc가 생성할 코드의 드라이버도 정해지지 않았다. 둘 다 새 의존성이라 결정이 필요하다.

**결정:**

- 마이그레이션 러너는 **`github.com/pressly/goose/v3`**. 라이브러리로 임베드해
  `make migrate`를 `go run`으로 처리한다.
- DB 드라이버는 **`github.com/jackc/pgx/v5`**. sqlc는 `pgx/v5` 타입으로 생성한다.
- sqlc 자체는 빌드 타임 도구다. 런타임 의존성이 아니며 `make doctor`에서 존재만 확인한다.

**대안과 기각 사유:**

- **golang-migrate** — 가장 널리 쓰이지만 CLI 설치가 전제이고 `make doctor` 확인 항목이 하나 는다.
  goose는 라이브러리 임베드로 별도 바이너리 없이 끝난다.
- **atlas** — 선언적 스키마 관리가 강력하나 이 규모에 무겁고,
  "순번 SQL 파일을 직접 작성하고 적용된 파일은 수정하지 않는다"는 기존 규약과 결이 다르다.
- **러너 없이 psql** — 의존성은 0이지만 적용 이력 추적을 직접 만들게 되고, 결국 러너를 재발명한다.

**결과:**

- 개발자가 설치할 바이너리는 sqlc 하나로 유지된다. goose는 `go.mod`에 들어간다.
- 마이그레이션 파일명은 goose 규약(`NNNNN_설명.sql`, `-- +goose Up` / `-- +goose Down`)을 따른다.
  기존 규약의 "순번 SQL"과 충돌하지 않는다.
- River를 붙일 때 River 자체 마이그레이션이 따로 온다. 두 러너가 공존하게 되며,
  적용 순서(goose 먼저 → River)를 그때 명시한다.

## ADR-018 — HTTP 라우터는 chi
**상태:** Accepted (2026-08-19)

**맥락:** 라우터가 결정된 적이 없다. 문서 전체에 근거가 두 개뿐이었다 —
`ARCHITECTURE.md`·`CONVENTIONS.md`의 `srv := &http.Server{...}` 조각(표준 `net/http`)과
ADR-009의 "oapi-codegen으로 Go 서버 인터페이스를 생성한다".

**지금 정해야 하는 이유:** oapi-codegen은 **대상 라우터별로 다른 코드를 생성한다**
(`chi-server`, `std-http-server`, `echo-server`, `gin-server` …).
설정 파일에 대상을 적어야 하므로 `openapi.yaml`을 만드는 시점에 이미 정해져 있어야 한다.

**결정:**

- 라우터는 **`github.com/go-chi/chi/v5`**.
- oapi-codegen 생성 대상은 **`chi-server`**.
- 핸들러는 `http.HandlerFunc` 시그니처를 유지한다. chi 고유 타입을 핸들러 인자로 쓰지 않는다.
- 미들웨어는 표준 `http.Handler` 래퍼만 쓴다.

**대안과 기각 사유:**

- **표준 `net/http` (`std-http-server`)** — 의존성이 0이고 Go 1.22+ `ServeMux`의
  메서드·와일드카드 라우팅으로 라우팅만 보면 충분하다(이 프로젝트는 1.26.6).
  기각 이유는 라우팅이 아니라 미들웨어다. 세션 인증, 관리자·검수자 권한 분리,
  요청 로깅(`log/slog`), 패닉 복구, 요청 ID를 전부 직접 조립해야 한다.
  제품 코드가 아닌 곳에 시간을 쓴다.
- **echo / gin / fiber** — 자체 컨텍스트 타입을 쓴다.
  "`context.Context`는 항상 첫 인자", "외부 I/O는 인터페이스 뒤에"라는 기존 규약과 결이 다르고,
  핸들러가 프레임워크에 묶여 나중에 갈아타기 어렵다.

**결과:**

- **잠기지 않는다.** chi는 프레임워크가 아니라 라우터 + 미들웨어 모음이고 핸들러 시그니처가
  표준과 같다. 나중에 표준 `ServeMux`로 옮겨도 핸들러는 손대지 않는다.
  되돌리기 쉬운 결정이므로 여기에 더 시간을 쓰지 않는다.
- `go.mod` 런타임 의존성은 goquery / x/text / pgx / goose / chi 다섯이 된다.
- `AGENTS.md` 기술 스택 표의 백엔드 행에 반영한다.

## ADR-019 — 패키지 매니저는 pnpm, Node 패키지는 `web/` 하나
**상태:** Accepted (2026-08-19)

**맥락:** 슬라이스 1(골격)에 이미 프론트엔드 작업이 들어 있다 —
`web/`의 TanStack Start SSR과 `make generate`의 orval 실행.
**패키지 매니저가 정해지지 않으면 슬라이스 1을 시작할 수 없다.**
Go 쪽은 ADR-017·018로 막아뒀는데 TS 쪽만 비어 있었다.

**결정:**

- 패키지 매니저는 **pnpm**. 버전은 `package.json`의 `packageManager` 필드로 고정하고
  corepack으로 활성화한다.
- **Node 패키지는 `web/` 하나만 둔다. 루트 `package.json`을 만들지 않는다.**
- **orval은 `web/`의 devDependency**로 두고 설정에서 `../openapi.yaml`을 참조한다.
- `make generate`는 Makefile에서 `web/` 안의 스크립트를 호출한다.
  **Makefile이 유일한 진입점**이라는 규약은 그대로다.

**대안과 기각 사유:**

- **npm** — Node에 내장돼 추가 설치가 없다. "개발자가 설치할 바이너리를 늘리지 않는다"는
  ADR-017의 논리와 일관된다. 그럼에도 pnpm을 고른 것은 **엄격한 `node_modules` 구조** 때문이다.
  `package.json`에 없는 패키지를 import해도 동작해버리는 사고(phantom dependency)를 막는다.
  이 프로젝트는 생성 코드가 많아 의존 관계가 흐려지기 쉽다. corepack으로 설치 부담도 작다.
- **bun** — 가장 빠르지만 TanStack Start·Vite·orval 조합의 검증 사례가 상대적으로 적다.
  이 슬라이스의 목적이 "도구 체인이 실제로 도는가"인데, 변수를 늘리는 선택이다.

**결과:**

- lockfile은 `web/pnpm-lock.yaml` 하나다. 저장소에 Node 패키지가 둘이 되지 않는다.
- `make doctor`에 pnpm 확인 항목이 하나 는다. **함께 갱신할 것.**
- Railway `web` 서비스 빌드가 pnpm을 쓰도록 설정해야 한다. 배포 슬라이스에서 확인한다.
- 루트에 `package.json`이 없으므로 TS 도구를 저장소 전역에 두려면 이 결정을 먼저 뒤집어야 한다.

## ADR-020 — 빌드 타임 코드 생성기는 `go.mod`의 tool 디렉티브로 고정한다
**상태:** Accepted (2026-08-19). ADR-017의 sqlc 관련 서술을 보완한다 — 러너·드라이버 결정은 그대로다.

**맥락:** 슬라이스 1에서 `make generate`를 되살리려면 sqlc와 oapi-codegen이 실제로 실행돼야 한다.
ADR-017은 "sqlc 자체는 빌드 타임 도구다. 런타임 의존성이 아니며 `make doctor`에서 존재만 확인한다"고
적었고, 이는 설치된 바이너리를 전제한다. oapi-codegen은 아예 정해진 적이 없다.

전제를 그대로 따르면 개발자가 설치할 바이너리가 둘(`brew install sqlc`, `go install oapi-codegen`)이 된다.
이는 ADR-017이 golang-migrate를 기각할 때 쓴 논리("CLI 설치가 전제이고 `make doctor` 확인 항목이 하나 는다",
"개발자가 설치할 바이너리를 늘리지 않는다")와 정면으로 어긋난다.

**결정:** Go 1.24+의 `tool` 디렉티브로 둘 다 `go.mod`에 고정한다.

```
tool (
	github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen
	github.com/sqlc-dev/sqlc/cmd/sqlc
)
```

Makefile은 `go tool sqlc` / `go tool oapi-codegen`으로 부른다.
`make doctor`는 두 도구를 계속 확인하되, 확인 대상이 PATH의 바이너리가 아니라 tool 디렉티브다.

**대안과 기각 사유:**

- **brew / `go install`로 바이너리 설치** — ADR-017의 전제이지만 버전이 저장소에 박히지 않는다.
  생성 코드는 커밋되므로, 개발자마다 생성기 버전이 다르면 `make generate`가 diff를 만들어낸다.
  `go install`은 `GOPATH/bin`이 PATH에 없으면 조용히 실패한다.
- **생성 코드를 커밋하지 않고 빌드 때마다 생성** — 생성기 부재가 빌드 실패로 바로 드러나지만,
  "생성 코드는 커밋한다"는 기존 `.gitignore` 방침을 뒤집어야 한다. 이 슬라이스의 범위가 아니다.

**결과:**

- 개발자가 설치할 바이너리는 **0개**가 된다. corepack으로 pnpm을 켜는 것만 남는다.
- 생성기 버전이 `go.mod`에 박히므로 `make generate` 결과가 사람마다 같다.
  현재 sqlc v1.31.1 / oapi-codegen v2.8.0.
- `go.mod`의 indirect 블록이 커진다. **런타임 의존성은 늘지 않는다** —
  tool 디렉티브의 패키지는 `cmd/api`·`cmd/worker` 바이너리에 들어가지 않는다.
- 도구 버전을 올릴 때는 `go get -tool <path>@<version>` 뒤에 `make generate`로 diff를 확인한다.

# ADR-030 — 마이그레이션은 Railway pre-deploy 명령으로 실행한다
**상태:** Accepted (2026-08-20). ADR-022가 정한 순서(goose → River)는 그대로다.

**맥락:** `make migrate`는 `tools/migrate`를 `go run`으로 돌린다. 로컬에서는 손으로 친다.
Railway에는 그 자리가 없다 — 서비스를 띄우는 것만 하지
"이 명령을 한 번 실행" 하는 자리가 기본적으로 없다.

순서가 틀리면 바로 깨진다. `00003_auth.sql`이 `sessions`를 만드는데,
그 SQL 없이 새 API 코드가 뜨면 로그인마다 `relation "sessions" does not exist`다.
**스키마가 코드보다 먼저 가 있어야 한다.**

**결정:** Railway pre-deploy 명령에서 `tools/migrate`를 실행한다.
새 버전을 띄우기 **전에**, 배포당 **한 번만** 돈다.

**대안과 기각 사유:**

- **일회성 서비스를 두고 손으로 실행** — 통제는 확실하지만 사람이 잊는다.
  마이그레이션이 포함된 배포에서 한 번 잊으면 그대로 장애다.
  잊지 않는 것에 기대는 절차는 언젠가 잊힌다.
- **`api` 기동 시 자동 실행** — 설정이 필요 없지만 **인스턴스가 여럿이면 경합한다.**
  Railway는 배포 교체 중 구/신 버전이 잠깐 함께 뜬다.
  **ADR-022가 이미 같은 이유로 기각한 방식**이고, 그 기각 근거가 Railway에서 실제로 성립한다.

**"실패하면 배포가 막힌다"는 단점이 아니다.** 스키마가 맞지 않는 코드가 뜨는 것보다
안 뜨는 것이 낫다. 막히는 것이 원하는 동작이다.

**결과:**

- **Go Dockerfile이 `tools/migrate`도 이미지에 넣는다.** 그래야 pre-deploy가 부를 수 있다.
  런타임 이미지가 바이너리 두 개를 담게 되지만 distroless static이라 수 MB 차이다.
- **pre-deploy는 `api` 서비스에만 건다.** `worker`에도 걸면 배포마다 두 번 돈다 —
  goose가 멱등이라 사고는 안 나지만 의미 없는 실행이고, 어느 쪽이 먼저인지 헷갈린다.
- 로컬은 `make migrate` 그대로다. 진입점이 둘로 갈리지만 같은 바이너리를 부른다.
- River 마이그레이션도 같은 진입점에서 이어 돈다 (ADR-022). 순서가 코드에 있다.

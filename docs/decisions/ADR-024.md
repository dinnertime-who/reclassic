# ADR-024 — 같은 문단의 승인은 자문 잠금으로 직렬화한다
**상태:** Accepted (2026-08-19). ADR-005를 보완한다 — 뒤집지 않는다.

**맥락:** ADR-005와 `ARCHITECTURE.md` 불변식 3은 승인 트랜잭션의 2단계
`WHERE id=$4 AND status='pending'`이 동시 승인을 막는다고 적었다.
번역 슬라이스에서 그것을 처음 시험했고, **막지 못하는 경우가 있었다.**

`status='pending'` 조건은 **같은 제안**을 두 검수자가 동시에 승인하는 것만 막는다.
같은 문단의 **서로 다른** 제안을 동시에 승인하면 다르게 흐른다:

```
T1: 1단계 supersede → 확정본 없음, 아무것도 안 함
T2: 1단계 supersede → 확정본 없음, 아무것도 안 함   (T1이 아직 커밋 전)
T1: 2단계 P1 승인 (pending이므로 통과)
T2: 2단계 P2 승인 (pending이므로 통과)
T1: 3단계 확정본 INSERT
T2: 3단계 확정본 UPSERT — PK 충돌로 대기했다가 덮어씀
```

결과: 확정본은 1행이다(복합 PK가 지킨다). 그러나 **`approved` 제안이 2개 남는다.**
확정본이 가리키지 않는 제안이 승인 상태로 떠 있고, 검수 화면과 이력이 거짓말을 한다.

**재현했다.** 서로 다른 제안 둘을 동시에 승인하는 것을 40라운드 반복하니
거의 전부에서 `approved=2, 확정본=1`이 나왔다.
**단발 테스트로는 통과한다** — 처음에 그렇게 놓쳤다. 인터리빙이 맞아떨어져야 드러난다.

**결정:** 승인 트랜잭션 맨 앞에서 `(project_id, paragraph_stable_id)`에 대해
`pg_advisory_xact_lock`을 잡는다. 트랜잭션이 끝나면 자동 해제된다.

```sql
SELECT pg_advisory_xact_lock(hashtextextended(project_key || ':' || stable_id, 0));
```

**ARCHITECTURE의 3단계는 그대로 둔다.** 순서를 바꾸지 않고 앞에 잠금만 더한다.

**대안과 기각 사유:**

- **`SELECT ... FOR UPDATE`로 확정본 행 잠그기** — 첫 승인 때는 행이 없어 잠글 것이 없다.
  이 버그가 정확히 "확정본이 아직 없을 때" 나므로 아무것도 막지 못한다.
- **3단계(확정본 UPSERT)를 1단계보다 먼저 하고 그 뒤에 supersede** — 실제로 동작한다.
  PK 충돌로 두 번째 트랜잭션이 대기하므로, 그 뒤의 supersede는 첫 번째의 승인을 보게 된다.
  기각한 이유는 **문장 순서에 correctness가 걸린다**는 것이다. 나중에 누가 읽기 좋게
  순서를 되돌리면 조용히 깨지고, 단발 테스트로는 드러나지 않는다.
  자문 잠금은 의도가 코드에 드러난다.
- **직렬화 격리 수준(SERIALIZABLE)** — 맞는 답이지만 승인 외의 모든 트랜잭션에도
  재시도 처리를 넣어야 한다. 문제가 한 지점에 갇혀 있는데 전역 비용을 치를 이유가 없다.

**결과:**

- 승인은 문단 단위로 직렬화된다. 서로 다른 문단은 여전히 병렬이다.
  해시 충돌로 무관한 두 문단이 가끔 직렬화될 수 있으나 대기가 짧아 문제되지 않는다.
- **반복 테스트를 유지한다** (`TestConcurrentApprovalStress`).
  단발로는 잡히지 않는 버그라 라운드 수를 줄이지 말 것.
- 불변식 2(문단당 확정본 1개)는 여전히 스키마가 지킨다. 이 잠금이 지키는 것은
  **제안 상태와 확정본의 일관성**이고, 그것은 여러 행에 걸쳐 있어 제약으로 표현할 수 없다.

# ADR-037 — 목록 API 응답은 배열이 아니라 `{ items }` 객체다
**상태:** Proposed

**맥락:** 슬라이스 8이 첫 목록 API를 만든다. 도서는 22권이라 커서도 오프셋도 지금
필요하지 않다. 다만 응답을 **배열 그대로** 내면, 나중에 `nextCursor` 하나를 붙이는
순간 파괴적 변경이 된다. 뒤에 오는 모든 목록(검수 큐, 내 제안, 용어집)이 이 첫
모양을 따르게 되므로, 지금 정하지 않으면 그때마다 같은 결정을 반복한다.

이미 있는 `GET /projects/{id}/paragraphs/{stableId}/proposals`는 배열이다.
그건 문단 하나 안의 제안이라 페이지네이션 대상이 아니고, 이 결정의 소급 적용
대상도 아니다. **새로 여는 목록만** 객체로 감싼다.

**결정:** 목록 응답은 `{ "items": [ ... ] }`다. 페이지네이션 필드는 넣지 않는다.

나중에 커서가 필요해지면 `nextCursor`를 **같은 객체에 선택 필드로** 더한다.
배열을 객체로 바꾸는 마이그레이션이 생기지 않는다.

**대안과 기각 사유:**

- **배열을 그대로 낸다** — 지금 가장 짧다. 기각한다. 22권이 200권이 되는 순간
  모든 클라이언트가 응답 타입을 갈아엎는다. 첫 목록을 여는 비용에 비하면
  `{ items }` 한 겹은 싸다.
- **처음부터 커서를 넣는다** (`items` + `nextCursor: null`) — 필드가 비어 있는
  채로 계약에 남는다. 기각한다. 없는 페이지네이션을 있는 것처럼 보이게 한다.
  필요할 때 선택 필드를 더하는 쪽이 정직하다.

**결과:**

- `GET /books`, `GET /projects`, 관리자 확인 큐·사용자 목록이 이 모양을 쓴다.
- 기존 `listProposals`는 배열로 남긴다. 이 ADR을 이유로 바꾸지 않는다.

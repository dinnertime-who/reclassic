# ADR-042 — 스타일시트는 루트 라우트에서 부수효과로 import한다
**상태:** Accepted (2026-09-03). 프로덕션이 스타일 없이 떠 있던 장애를 닫는 결정이다.

**맥락:** 2026-09-03, 프로덕션 웹이 **스타일시트 없이** 떴다. 본문은 다 보이는데 조판이
전부 브라우저 기본값이었다 — `main` 폭이 1664px(672px이어야 한다), `h1`이 32px.

원인은 `__root.tsx`의 두 줄이었다.

```js
import appCss from '../styles.css?url'
...
links: [{ rel: 'stylesheet', href: appCss }]
```

`?url`은 **빌드 시점에 그 빌드가 낸 자산의 URL로 굳는다.** 그런데 SSR 앱은 Vite 빌드를
두 번 돈다 — 클라이언트 빌드는 `.output/public/assets/`에 발행하고, SSR 빌드는 자기
자산을 따로 낸다. `head()`는 **SSR에서 실행되므로** 렌더된 `<link href>`에는
**SSR 빌드의 해시**가 박힌다. 그 파일은 `.output/public`에 발행되지 않는다.

**지금까지 돌아간 것은 운이었다.** 두 빌드가 낸 CSS 내용이 바이트 단위로 같으면 콘텐츠
해시도 같아져 링크가 우연히 맞는다. 실제로 깨졌을 때 두 파일은 **47.91 kB(SSR)과
34.02 kB(클라이언트)**로 갈라져 있었다.

**이 버그는 우리 게이트를 전부 통과한다.** `make lint`·`make test`·`make docs-check`가
다 초록이고, 빌드도 배포도 성공하고, `/healthz`의 version도 머지 커밋과 일치한다.
**로컬 `pnpm build`로도 재현되지 않았다** — Docker 이미지를 만들어 컨테이너를 띄웠을 때
비로소 드러났다. 이미지 안에는 CSS가 하나뿐인데 SSR 번들은 없는 이름을 참조하고 있었다.

**결정:**

1. **스타일시트는 루트 라우트에서 부수효과로 import한다** — `import '../styles.css'`.
   번들러가 클라이언트 자산을 문서에 주입하므로 발행된 파일 하나만 참조된다.
2. **`?url`로 받은 값을 `head().links`에 직접 넣지 않는다.** 자산 URL을 손으로 만드는
   순간 어느 빌드의 것인지가 실행 위치에 따라 갈린다.
3. **배포 확인을 `/healthz`의 version 일치로 끝내지 않는다.** 실제로 렌더된 화면을 본다.

**대안과 기각 사유:**

- **두 빌드가 같은 CSS를 내도록 압축 설정을 맞춘다** — 해시가 같아져 지금은 고쳐진다.
  기각한다. **그것이 바로 지금까지의 상태였다.** 두 출력이 우연히 같기를 계속 기대하는
  것이고, 갈라지는 날 똑같이 조용히 깨진다.
- **Dockerfile을 고친다** — 처음에 의심한 곳이다. 기각한다. `COPY --from=build
  /app/web/.output ./.output`은 통째로 복사하고 걸러내는 것이 없다. 같은 디렉터리의 JS는
  멀쩡히 서빙됐다. **Docker는 두 출력이 갈라진 환경일 뿐 원인이 아니다.**
- **`<link>`를 손으로 쓰되 클라이언트 매니페스트에서 이름을 읽는다** — 동작은 한다.
  기각한다. 번들러가 이미 하는 일을 우리가 다시 구현하는 것이고, 프레임워크가 자산
  이름 규칙을 바꾸면 또 깨진다.

**결과:**

- 이미지 안 CSS가 하나로 합쳐지고(`index-*.css`) SSR HTML이 그것을 가리킨다.
  Docker 컨테이너에서 `200 · text/css · 34,020바이트`로 확인했다.
- **`<link>`는 여전히 SSR HTML 안에 있다.** 무자바스크립트 렌더 조건(ADR-007·023)이 유지된다.
- **이 유형은 Docker 이미지로만 검증된다.** 자산 경로·발행 여부를 건드리는 변경은
  `make docker-build-web`으로 이미지를 만들고 컨테이너를 띄워 확인한다.
  `make lint`·`make test`로는 잡히지 않는다.

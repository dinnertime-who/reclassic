# ADR-026 — 브라우저의 교차 출처 호출은 출처 허용목록으로 받는다
**상태:** Accepted (2026-08-19)

**맥락:** 읽기 화면에서 다음 챕터를 누르면 `Failed to fetch`가 났다.

첫 진입은 SSR이라 **서버가** API를 부르고, 그 뒤 라우터 이동은 **브라우저가** 직접 부른다.
웹과 API는 출처가 다르므로(로컬 `:3100` / `:8080`) 후자는 교차 출처 요청이다.
Go API에 CORS 미들웨어가 없어 브라우저가 응답을 버렸고, `OPTIONS`는 405였다.

**로컬만의 문제가 아니다.** `ARCHITECTURE.md` 불변식 4가
"SSR 서버가 API를 호출할 때는 `서비스명.railway.internal`을 쓴다. 브라우저는 공개 도메인을 쓴다"고
정했으므로, 프로덕션에서도 브라우저 → API는 언제나 교차 출처다.

**결정:** `github.com/go-chi/cors`를 미들웨어로 붙이고,
허용 출처를 `CORS_ALLOWED_ORIGINS`(쉼표 구분)로 받는다. 없으면 기동 실패.

- **와일드카드(`*`)를 쓰지 않는다.** 클라이언트가 `credentials: 'include'`로 보내므로
  규격상 `*`가 허용되지 않고, 허용해서도 안 된다 —
  아무 사이트나 사용자 세션으로 이 API를 부르게 된다.
- 허용 헤더에 `X-Admin-Token`, `X-User-Handle`을 넣는다.
  커스텀 헤더는 preflight 대상이라 빠뜨리면 `OPTIONS`에서 막힌다.
- 허용 메서드는 `GET`, `POST`, `OPTIONS`뿐이다. 지금 계약에 다른 메서드가 없다.

**대안과 기각 사유:**

- **직접 구현** — 의존성이 늘지 않는다. 기각한 이유는 CORS가 조용히 틀리기 쉽기 때문이다.
  출처 반사, `Vary` 누락, preflight 캐시, credentials 조합에서 하나만 어긋나도
  보안 구멍이거나 디버깅하기 어려운 실패가 된다.
  ADR-018이 표준 `net/http`를 기각할 때 쓴 논리와 같다 — 제품 코드가 아닌 곳에 시간을 쓰지 않는다.
- **Vite 개발 서버 프록시로 같은 출처 만들기** — 로컬에서는 되지만 프로덕션에서 안 된다.
  개발과 프로덕션의 요청 경로가 달라져, 로컬에서 통과한 것이 배포 후 깨진다.
- **브라우저도 SSR을 거치게 하기(server function 경유)** — 비즈니스 로직이
  server function으로 새는 길이고 ADR-006이 금지한다.

**결과:**

- 런타임 직접 의존성이 일곱이 된다. `go-chi/cors`는 chi 계열이라 미들웨어 시그니처가 표준과 같다.
- **LAN이나 Tailscale로 접속하려면 그 출처도 목록에 넣어야 한다.**
  `make run-web-lan`을 쓸 때 `CORS_ALLOWED_ORIGINS`에 `http://192.168.x.x:3100`을 추가한다.
  잊으면 첫 화면만 뜨고 챕터 이동이 막힌다 — 증상이 이 ADR을 만든 그것과 같다.
- 세션 인증(슬라이스 5)이 붙으면 쿠키가 이 경로로 오간다.
  `AllowCredentials: true`와 출처 허용목록이 그때 실제로 값을 한다.
